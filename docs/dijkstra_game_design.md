## 2. ゲーム設計

### 2.1 学習目標と対応する仕掛け

| # | 学習目標 | 体験させる場所 | 具体的な瞬間 |
|---|---|---|---|
| 1 | 近い順に確定させる。未確定のうち札が最小の地点の値は覆らない | 層B | 札が最小でない地点を選ぶとミスになり、「ほかの候補を経由すると早く着ける」理由が示される(3.6) |
| 2 | ラベルを更新する(緩和)。より近い行き方が見つかったら暫定値を書き換える | 層B | Stage 1 `D: 9→6`、Stage 2 `B: 13→8`、Stage 3 `D: 12→10`, `G: 16→14` |
| 3 | 直感が外れる。見た目に近い道が最短とは限らない | 層A | Stage 2の直線ルート(18)が最短(9)の2倍 |

- 目標2の緩和はゲームが自動で行う。プレイヤーに緩和を判定させる「上級管制室」は、5〜10分で初見の来場者には重いので作らない(将来機能)。
- 目標3を効かせるため、道の所要時間(重み)は原則として線の長さにおおむね比例させ、罠の道だけを意図的に外す(3.3)。こうすると、ふだんは見た目が当てになり、罠のところで直感が外れる。

### 2.2 ゲームループ(2層構造)

#### 層A: 配達モード(直感で遊ぶ)

1. 地図に倉庫(S)とお届け先(G)が表示される。道には所要時間が書いてある。
2. プレイヤーは隣接する交差点を順にタップしてルートを作る。同じ交差点は2度通れない。
3. 未訪問の交差点だけを通ってGへ行けなくなったら、「ここからはお届け先に行けません。戻ってください」と表示する。
4. Gに到達すると総所要時間が確定し、星(1〜3)が付く。
5. 最短ルートを「ゴースト」として重ね、到着時間マップを解放する。

#### 層B: 管制室モード(アルゴリズムを手で実行する)

ダイクストラ法そのものを、プレイヤーの手で1手ずつ進める。

1. 各交差点に**札**を持たせる。札は「Sからここまで、今わかっている中でいちばん早い時間」のメモで、初期値はSが0、ほかは∞とする。
2. プレイヤーは「未確定のうち札が最小の交差点」を選んで**確定**する。確定とは、「この交差点への最短時間はこれで決まり」と認めることである。
3. ゲームは、確定した交差点から出る道を1本ずつ光らせ、隣の札を見直す(**緩和**)。書き換えるのは、値が小さくなる場合だけとする(演出は2.3)。
4. 札が最小でない交差点を選ぶと、ミスとして数え、確定はさせない。理由を示すメッセージを出す(3.6)。
5. Gが確定したらクリアとし、ミス回数と星を表示する。到着時間マップと最短経路木を解放する。
6. クリア後は「続けて全地点を確定」を選べる(採点対象外)。1回の実行で全地点への最短が求まることを体験させるための機能である。

#### 進め方

Stage 1 の層A→層B、Stage 2 の層A→層B、Stage 3 の層A→層B の順に、クリアするたびに自動で進める。各層の後には種明かし(2.8)を挟む。層Aを先にするのは、自分の直感で解いた結果を見てからアルゴリズムに触れる順にするためである。

メニューから、ステージと層を自由に選ぶこともできる(ロックなし)。

### 2.3 演出

| 演出 | 狙い | 表示タイミング | 時期 |
|---|---|---|---|
| 波紋アニメーション(確定時に円が広がる) | 「近い順に確定する」を視覚化する | 層Bの確定時 | MVP |
| フロンティアの強調(暫定値を持つ未確定の交差点) | 次の候補がどれかを示す | 層Bで常時 | MVP |
| 札の更新の要約(例: `A: ∞→4, B: ∞→3`) | 緩和の結果を残す | 層Bの確定時(1回の確定での更新をまとめて1行) | MVP |
| 緩和の1本ずつの表示 | 「書き換えるのは早くなるときだけ」を目で確かめさせる | 層Bの確定時(下記) | 10/26 |
| ミス時の経由ルートの強調 | 札が最小でない交差点を選べない理由を示す | 層Bのミス時(3.6) | MVP |
| ゴーストルート(最短経路の点線) | 自分の解との差を実感させる | 層Aのクリア後 | MVP |
| 到着時間マップ(全交差点を最短時間で色分け) | 1回の実行で全地点への最短が求まることに気づかせる | 各層のクリア後のみ(ネタバレ防止) | MVP |
| 最短経路木(`prev` の辺を太線で重ねる) | 全地点への最短ルートを重ねると枝分かれした木になることを見せる | 層Bのクリア後、到着時間マップと一緒に | 10/26 |

- 到着時間マップは、交差点を色で塗り分ける表示とする。「5分圏」のような境界線は引かない。道の途中の時間を補間する方法を別に決める必要があり、手間に見合わないためである(旧称「等時線ヒートマップ」)。
- 緩和の1本ずつの表示では、確定した交差点から出る道を順に光らせ、道の横に計算を出す。1本あたり約0.6秒とし、確定済みの交差点へ向かう道は飛ばす。「そのまま」の道も見せる。例: Stage 1 でD(6)を確定したとき
  - C: `6+3=9`、今の札は 9 → そのまま
  - F: `6+7=13`、∞ → 13
  - H: `6+3=9`、∞ → 9
- 演出の途中で次の交差点が押されたら、演出を飛ばして最後の状態にしてから受け付ける。
- 最短ルートが複数あるとき
  - 層Aのゴースト: プレイヤーのルートが最短なら、そのルートをゴーストとして示し、「ほかにも同じ時間のルートがあります」と添える。最短でなければ、`prev` から求めた1本を示す。
  - 最短経路木: 同点の場合は `nodes` の記述順で1本を選ぶ(3.4)。木が1本に決まらないことは扱わない。

### 2.4 ステージ構成

| Stage | 名称 | 内容 | 学べること | 時期 |
|---|---|---|---|---|
| 1 | 下町 | 10頂点未満、基本ルール | 基本 | MVP |
| 2 | 高速道路 | 遠回りだが速い道がある | 見た目の距離と重みは別物 | MVP |
| 3 | 一方通行 | 有向辺 | 有向グラフ | MVP |
| 7 | 大都市 | 数百頂点。プレイヤーは操作せず、自動実行を見る。輻輳デモを含む | アルゴリズムなら一瞬で解ける。混雑に応じて経路を計算し直す | 10/26 |
| 6 | ボーナス道路 | 負の辺 | ダイクストラの限界、ベルマン–フォード | 10/26より後 |
| 8 | 空港ラッシュ | 方向の手がかり | A*(ヒューリスティクス) | 10/26より後 |

- 番号は旧計画のまま残す。旧Stage 4「通行料金」(重みが料金)と旧Stage 5「工事渋滞」(途中で重みが変化)は削除した。Stage 4の要点「重みは時間でなくてもよい」は、種明かしの一言で伝える。Stage 5の「重みの変化と再計算」は、Stage 7の輻輳デモで見せる。
- 遊ぶ順は 1 → 2 → 3 → 7 とする。

#### Stage 7「大都市」と輻輳デモ

1. 数百頂点の街を表示し、Sから全地点への最短を自動で一瞬で求め、到着時間マップを出す。人間が1つずつ確定していたら終わらない量を、アルゴリズムなら一瞬で解けることを見せる。
2. 続けて輻輳デモに移る。配達車を次々に出発させ、各車は出発時点の所要時間でダイクストラ法を実行してルートを決める。
3. 通っている車が多い道ほど所要時間が延び、色が変わる。後から出る車は、そのときの所要時間で最短を計算し直すので、混雑を避けて迂回する。
4. 車が道を抜けると、その道の混雑は戻る。

インターネットのルーティング(OSPFなど)で負荷を分散するのと同じ考え方である。具体的な値(頂点数、配達車の数と出発間隔、混雑による所要時間の延び方)と、大きい街の作り方(格子を崩す、ドロネー三角形分割など)は、10/26の作業に入る前に決める(5章)。

#### Stage 6「ボーナス道路」(10/26より後)

非負条件が崩れると「確定したはずの値が後から覆る」ことを見せ、その後にベルマン–フォード法を紹介する。全体の山場になる。

- 負の辺は有向辺(一方通行のボーナス道路)に限る。無向辺に負の重みを付けると、その辺を往復するだけで負の閉路になり、最短距離が定まらないためである。
- 負の閉路を作らない。
- この2点を `validateStage` で確かめる(3.3)。

### 2.5 採点

| 層 | ★3 | ★2 | ★1 |
|---|---|---|---|
| 層A | `cost == opt` | `cost <= star2`(ステージごとに定義)| それ以外 |
| 層B | ミス0 | ミス1〜2 | ミス3以上 |

- `star2` は、次善のルート程度なら★2になるよう、ステージデータで個別に指定する。一律に `opt × 1.25` とすると、Stage 2では次善(12)でも★1になり、ステージ間で難度がばらつくためである。
- ヒントを使ったラウンドは、ヒントの段階に応じて星の上限を下げる(2.6)。
- 星の保存は10/26までに作る。保存先(端末内かDjangoか)は、Djangoへ組み込むときに決める(5章)。

### 2.6 ヒント(10/26)

| 段階 | 層A | 層B |
|---|---|---|
| ① | 現在地から進める交差点を光らせる(減点なし) | 候補のうち札が最小のものを光らせる(★2が上限) |
| ② | 現在地からGへの最短で次に進む交差点を光らせる(減点なし) | 正解を1手自動で確定(★1が上限) |
| ③ | 最短ルートを表示(★1が上限) | なし |

- 層Bでは候補(フロンティア)が常に強調されているので、「候補を光らせる」ヒントは置かない。「最小の候補を光らせる」は答えそのものなので、減点の対象にする。
- 層Aのヒント②は「現在地から」の最短を示すので、プレイヤーがすでに遠回りしていても次善の一手を示せる。この一手は、Gからの逆向き最短距離(3.4の `distToGoal`)で求める。

### 2.7 設計上の落とし穴と対策

| 問題 | 対策 |
|---|---|
| 小さいグラフは目視で解けてしまう | 「見た目は近いが重みが大きい」罠を意図的に配置する(Stage 2) |
| 重みが線の長さと無関係だと、見た目を無視して数字を足すことを覚え、罠に掛からなくなる | 罠でない道は、重みを線の長さにおおむね比例させる(3.3) |
| 同点の最短路があると採点が曖昧になる | 経路ではなくコストで判定し、最短ならどの経路でも正解とする(Stage 3は同点2経路) |
| 層Bで同値の候補が複数ある | どれを選んでも正解とする。ただし、教えたい緩和がタイ順に依存しないようデータを調整する(Stage 2のS-Aを4にした理由) |
| 層Bで、札が最小でない交差点の値がたまたま正しいことがある | 判定は規則どおり(最小でなければミス)とし、メッセージで「たまたま合っている」ことを伝える(3.6) |
| 層Aで、隣に未訪問の交差点はあるのにGへ行けない袋小路に入る | 未訪問の交差点だけでGに到達できるかで判定し、行けなければ戻るよう促す(例: Stage 1の `S-B-D-F-C`) |
| 負の辺の扱い | 有向辺に限り、負の閉路を作らない。Stage 6でダイクストラの失敗を見せてからベルマン–フォードを導入する |
| 層Bで画面が混雑する | 小さいグラフから始め、ハイライトで視線を誘導する |
| 到着時間マップ・ゴーストを見ると答えが分かる | クリア後にのみ解放する |

## 3. 実装設計

### 3.1 技術選定

| 項目 | 方針 | 理由 |
|---|---|---|
| 計算の場所 | 最短経路の計算、ラウンドの判定、ステージの検証は、すべてブラウザのJSで行う | MVPの9頂点なら一瞬、Stage 7(数百頂点)でも数ミリ秒で済む。サーバと通信せずに遊べる |
| Djangoの役割 | 配信と記録の保存だけ。ステージをDjango側で管理することはしない | 計算をブラウザに置くので、サーバに要るのは配る・残すだけになる |
| 言語 | JavaScript(ESモジュール)。ビルドなし・外部ライブラリなし。型はJSDocで補う | 静的ファイルとして置くだけで動く。今日のMVPは静的サーバで動かし、そのままDjangoの静的ファイルにできる |
| 描画 | SVG | `viewBox` で画面幅に合わせて拡大縮小できる。ノードごとにタップ判定を付けられる。状態の見た目をCSSで切り替えられる |
| 対象ブラウザ | ChromeOSのChrome(最新版)。開発時はPCのChrome | 貸与端末に合わせる |
| 入力 | タッチとタッチパッド(マウス)の両方 | C425はどちらも使える |
| テスト | `node --test`(Nodeは開発時のみ必要) | ロジックをDOM非依存にしておけば、ブラウザなしで検証できる |

### 3.2 ファイル構成

```
apps/dijkstra-delivery/
├── package.json          # {"type": "module"} のみ。テストを Node で ES モジュールとして読むため
├── static/               # 配信されるのはここだけ
│   ├── index.html
│   ├── style.css
│   ├── main.js           # 起動、入力 → ラウンド → 描画の接続、自動進行
│   ├── logic.js          # グラフ・最短経路・ラウンド状態(DOM 非依存)
│   ├── stages.js         # ステージデータと validateStage
│   ├── view.js           # SVG 描画・演出
│   └── config.js         # 調整用の値(大きさ、間隔)
└── tests/
    ├── logic.test.js     # 最短経路
    ├── delivery.test.js  # 層A
    ├── control.test.js   # 層B
    └── stages.test.js
```

- アプリ内のファイルは相対パス(`./logic.js`)で参照する。こうすると、単体の静的サーバでもDjangoの静的ファイルでも同じファイルが動く。
- ステージデータはJSONファイルにせず、JSモジュールとして書く。ブラウザでもテストでも `import` だけで読めるので、`fetch` の非同期処理が要らない。
- Djangoへの組み込み方(置き場所、テンプレート、記録のAPI)は10/26までに決める。星の保存と記録のファイルは、そのときに足す。

### 3.3 データ構造

```js
/**
 * @typedef {{
 *   u: string, v: string, w: number,
 *   directed?: boolean,
 *   kind?: "road" | "highway",
 *   trap?: boolean,                        // 重みと長さの比の検査から外す罠の道
 * }} Edge
 * @typedef {{
 *   id: string,                            // 進捗保存のキー。並べ替えや追加で変えない
 *   name: string, desc: string,
 *   nodes: Record<string, [number, number]>, // 名前 → 座標(viewBox 1600×900 基準)
 *   edges: Edge[],
 *   expectedCost: number,                  // 設計値。テストで dijkstra() と照合する
 *   star2: number,                         // 層Aで★2となるコストの上限
 *   start?: string, goal?: string,         // 既定は "S" と "G"
 *   allowNegative?: boolean,               // Stage 6 のみ true
 * }} Stage
 */
export const INF = Infinity;
// 隣接表: Map<u, Map<v, weight>>(無向辺は両方向を登録)
```

- 座標は16:9の viewBox 1600×900 を基準とし、横画面専用とする。

#### `validateStage(stage)`

テストで全ステージに適用し、次の条件をすべて満たすことを確かめる。

- 辺の端点、`start`、`goal` がすべて `nodes` に存在する。
- 同じ向きの辺が重複しない。重複すると隣接表で上書きされるためである。無向辺は両向きとして数える。
- 重みが正の整数である。`allowNegative` のステージだけ、有向辺に限って負の整数も認める。その場合も負の閉路がないこと(ベルマン–フォード法で検出)を確かめる。
- `goal` が `start` から到達可能である。
- 座標がviewBoxの内側にある(余白60)。ノード間の距離が150以上ある(タップ判定の円 r=60 が重ならない)。辺が他のノードの上を通らない(ノード中心と辺の距離が60以上)。
- `id` がステージ間で重複しない。
- 重みと線の長さの比(10/26、ステージの作り直し後に有効にする): 基準長を100とし、`重み ÷ (線の長さ ÷ 100)` が、一般の道は0.7〜1.3、`kind: "highway"` は0.3〜0.5に収まる。`trap: true` の道は検査しない。

大きさの数値(余白、ノード間距離、タップ判定の半径)は仮の値である。C425の実機で押しやすさを確かめて決める(5章)。

### 3.4 コアロジック(`logic.js`)

```js
export function buildAdj(stage, { reverse = false, undirected = false } = {}) {
  const adj = new Map(Object.keys(stage.nodes).map((n) => [n, new Map()]));
  for (const e of stage.edges) {
    const [u, v] = reverse ? [e.v, e.u] : [e.u, e.v];
    adj.get(u).set(v, e.w);
    if (!e.directed || undirected) adj.get(v).set(u, e.w);
  }
  return adj;
}

// 確定集合を持つ O(V²) 版。数百頂点(Stage 7)まではこれで足りる
export function dijkstra(adj, s) {
  const dist = new Map([...adj.keys()].map((n) => [n, INF]));
  const prev = new Map();
  const done = new Set();
  dist.set(s, 0);
  for (;;) {
    let u = null;
    for (const [n, d] of dist) {
      if (!done.has(n) && d < INF && (u === null || d < dist.get(u))) u = n;
    }
    if (u === null) break;
    done.add(u);
    for (const [v, w] of adj.get(u)) {
      const nd = dist.get(u) + w;
      if (!done.has(v) && nd < dist.get(v)) {
        dist.set(v, nd);
        prev.set(v, u);
      }
    }
  }
  return { dist, prev };
}

/** s から g への経路。到達不能なら null */
export function pathTo(prev, s, g) {
  if (g !== s && !prev.has(g)) return null;
  const path = [g];
  while (path.at(-1) !== s) path.push(prev.get(path.at(-1)));
  return path.reverse();
}

/** 各ノードから goal への最短距離(層Aヒント②用)。辺を逆向きにして goal から解く */
export function distToGoal(stage) {
  return dijkstra(buildAdj(stage, { reverse: true }), stage.goal ?? "G").dist;
}

/** from から、visited を通らずに goal へ行けるか(層Aの行き止まり判定用) */
export function canReach(adj, from, goal, visited) {
  // from からの深さ優先探索。visited に含まれるノードには入らない
}
```

- ヒープは使わない。JSには標準の優先度キューがなく、この規模なら線形探索で十分に速い。Stage 7の輻輳デモで配達車ごとに実行して遅ければ、そのときに見直す。
- 同じ距離の候補が複数あるときは、`nodes` の記述順で先にあるものを選ぶ。こうして結果を決定的にする。
- 負の辺についての注意(Stage 6): この `dijkstra()` は確定済みノードを再更新しないので、負の辺があると誤った答えを返す。Stage 6の失敗デモでは、この性質を `ControlRound`(3.5)で見せる。Stage 6の正解(`opt`)は `bellmanFord()` で求める。

### 3.5 ゲーム状態とモジュール設計

ラウンドの状態と判定はDOMに依存しないクラスに置く。画面側はその結果(種類と更新内容)を受け取り、描画と演出だけを行う。

#### `DeliveryRound`(層A、`logic.js`)

| 項目 | 内容 |
|---|---|
| 状態 | `route: string[]`、`finished: boolean`、`hintLevelUsed: number` |
| `tap(n) -> { kind, ... }` | `kind`: `added` / `undone` / `invalid` / `stuck`(追加後、未訪問の交差点だけではGへ行けない)/ `finished` |
| `undo()` | 1手戻る(ボタン用) |
| `cost()` / `stars()` | 2.5の採点 |
| `ghost()` | クリア後に重ねる最短ルート `path` と、同じ時間のルートがほかにもあるか `tie`(2.3) |

#### `ControlRound`(層B、`logic.js`)

| 項目 | 内容 |
|---|---|
| 状態 | `dist`(札)、`done: Set`、`prev`、`mistakes`、`finished`、`hintLevelUsed` |
| 正解 `opt` | 生成時にステージから `dijkstra()` で求める(`dist`・`prev`)。ミス時の理由を求めるのに使う。Stage 6 では `bellmanFord()` の結果を渡せるようにする |
| `candidates()` | 未確定かつ `dist` が有限のノード |
| `settle(n) -> { kind, ... }` | `kind`: `settled` / `already` / `unreached` / `not_min`(3.6)。G を確定したときも `settled` で、`finished` が true になる |
| `stars()` | 2.5の採点 |

- `settled` のとき、`relaxations: { node, via, from, cand, updated }[]` を返す。確定したノードから未確定のノードへ出る辺ごとに、元の札 `from`、候補値 `cand = dist[via] + w`、書き換えたか `updated` を持つ。画面はこれを使って、要約1行(`updated` のものだけ)と1本ずつの演出(すべて)を出す。
- `not_min` のとき、状態は変えず(`mistakes` だけ +1)、理由 `reason` を返す(3.6)。`reason` は `{ kind: "overturn", via, viaDist, best, path }`(実際に覆る。`path` は c から n までの最短ルート)か `{ kind: "lucky", minNodes }`(たまたま合っている)。

`ControlRound` は確定集合を持つ教科書どおりのダイクストラ法なので、次の用途にもそのまま使える。

- 自動実行(Stage 7): 「候補の最小を選んで `settle()`」を繰り返すだけで実現できる。
- Stage 6の失敗デモ: 緩和によって確定済みノードの値が改善される場合、それを `violations` として記録して演出する。

#### `main.js`(画面の制御)

| 項目 | 内容 |
|---|---|
| 状態 | `stageIndex`、`mode`(`"A"` / `"B"`)、`opt`(`dist`・`prev`。ステージ読込時に計算)、`goalDist`(`distToGoal`)、`delivery`、`control`、`showMap`、`hintNodes` |
| 自動進行 | ラウンドがクリアされたら、2.2の順で次のステージ・層へ進める(MVPでは「次へ」ボタン) |
| `loadStage()` / `reset()` | ラウンドを作り直し、演出レイヤーを空にする(実行中のアニメーションも消える) |
| 入力 | ノードの当たり判定円の `click`(タッチ・タッチパッド共通)を、モードに応じたラウンドに渡す |
| `render()` | 状態に合わせてSVGの属性とメッセージ欄を更新する(`view.js`) |

#### `view.js`(描画)

- SVGは `<g>` で4層に分け、下から辺、ノード、文字(重み・札)、演出の順に重ねる。`render()` は演出層に触れないので、再描画しても波紋は消えない。
- 波紋は、演出層に円を追加し、CSSアニメーション(`transform: scale` と `opacity`)で広げ、`animationend` で削除する。

### 3.6 各モードのルール実装

#### 層A(配達)

`DeliveryRound.tap(n)` は、タップされたノード `n` を次の順に判定する。

```
n == route[-2]                                  → 1手戻る(undone)
n が route[-1] から辺で行ける未訪問ノード       → 追加(added)
    n == G                                      → 終了(finished)。星を計算
    n から、未訪問ノードだけを通って G へ行けない → stuck(「ここからはお届け先に行けません。戻ってください」)
それ以外                                        → invalid(「そこへは直接行けません」)
```

- 「辺で行ける」かどうかは、有向辺なら向きに従って判定する。
- `stuck` の判定は `canReach(adj, n, G, route)` で行う。隣に未訪問の交差点がない場合(例: Stage 1の `S-B-D-H-E`)だけでなく、隣に未訪問の交差点があってもGへ抜けられない袋小路(例: Stage 1の `S-B-D-F-C`。Cの隣のAは未訪問だが、Aの先はすべて訪問済み)も検出する。
- ツールバーの「1手戻る」ボタンでも同じ操作ができる。
- 終了時には最短経路を点線(ゴースト)で重ねる(同点の扱いは2.3)。

#### 層B(管制室)

`ControlRound.settle(n)` は、選ばれたノード `n` を次の順に判定する。

```
m = min(dist[c] for c in candidates())
n が確定済み      → already  「確定済みです」            (ミスに数えない)
dist[n] == ∞      → unreached「まだ届いていません」       (ミスに数えない)
dist[n] > m       → not_min  (ミス+1。確定はしない。メッセージは下記)
それ以外          → settled。出る辺を緩和する
                    n が G なら finished
```

- 同値の候補が複数ある場合は、どれを選んでも正解とする。
- ミスに数えるのは、アルゴリズムの規則を誤解した選択(`not_min`)だけとする。`already` と `unreached` は押し間違いの可能性が高いため数えない。
- 判定は、値が後で実際に覆るかどうかではなく、規則(札が最小か)で行う。結果で判定すると、「最小を選べば必ず正しい」というダイクストラ法の保証を教えられないためである。

#### `not_min` のメッセージ

札が最小でない交差点の値は、たまたま正しいことがある。たとえば Stage 1 でSを確定した直後は、B(3)とA(4)が候補になる。ここでAを選ぶと規則違反だが、Aの4は最終的な最短距離と同じである。そこで、`opt.dist[n]`(本当の最短距離)と比べてメッセージを2通りに分ける。

| 場合 | 条件 | メッセージ | 地図 |
|---|---|---|---|
| 実際に覆る | `dist[n] > opt.dist[n]` | 「まだ確定していない c(札 `dist[c]`)を経由すると、n には `opt.dist[n]` で着けます」 | c から n までのルートを光らせる |
| たまたま合っている | `dist[n] == opt.dist[n]` | 「札が `dist[n]` より小さい候補が残っています。今回はたまたま合っていますが、この時点では保証できません」 | 札が最小の候補を光らせる |

c は、`pathTo(opt.prev, S, n)` のルート上で最初に現れる未確定のノードとする。c の1つ手前は確定済みで、その札は正しい値なので、c はすでに候補になっており、札は本当の最短距離に等しい。したがって `dist[c] <= opt.dist[n] < dist[n]` となる。これはダイクストラ法の正しさの証明に出てくる性質そのもので、「なぜ最小から確定するのか」の答えになる。

例: Stage 1 でS・Bを確定した直後(候補はA(4)、E(7)、D(9))にDを選ぶと、Dの本当の最短は6(`S-A-D`)なので、「まだ確定していない A(札 4)を経由すると、D には 6 で着けます」と出す。

### 3.10 テスト計画

#### 単体テスト

`node --test apps/dijkstra-delivery/tests/` で実行する。ブラウザは要らない。

- 全ステージで `validateStage()` が通る。条件に違反するステージ(負の重み、無向の負の辺、負の閉路、重複辺、到達不能なゴールなど)を作ると、それぞれ検出される。
- 全ステージで、`dijkstra()` が求めた `goal` までの距離が `expectedCost` と一致する。
- Stage 3を `undirected: true` で解くと12、有向グラフとして解くと14になる(有向辺が逆向きに使われていない)。
- 到達不能ノードの `dist` が `INF` のまま残り、`pathTo()` が `null` を返す。
- `distToGoal()` が有向辺の向きを正しく反転している(Stage 3でAから11)。
- `DeliveryRound.tap()` の5分岐が正しく動く。`stuck` は Stage 1の `S-B-D-H-E` と `S-B-D-F-C` の両方で出る。
- `ControlRound.settle()` の4分岐(`settled` / `already` / `unreached` / `not_min`)が正しく動き、ミスが `not_min` のときだけ増える。`not_min` のあと状態が変わらない。
- `not_min` の理由: Stage 1でS確定後にAを選ぶと「たまたま合っている」、S・B確定後にDを選ぶと「実際に覆る」で `c = A`、`dist[c] = 4`、本当の最短6になる。
- 3.9の「層Bの進行」どおりに `settle()` したとき、`relaxations` のうち `updated` のものが記載どおりになる(Stage 2の `B: 13→8` など)。「そのまま」の辺も含まれている(Stage 1のD確定時のC)。
- `ControlRound` を自動実行した結果が `dijkstra()` の結果と一致する。
- 星判定: 各ステージで最適、`star2` ちょうど、`star2 + 1` のコストを判定する。層A・層Bそれぞれのヒントによる上限も確認する(ヒントは10/26)。

#### 手動テスト

PCのChromeと、C425のChrome(タッチとタッチパッドの両方)で確認する。

- 層A: 通れない辺のタップ、1手戻し(タップ・ボタンの両方)、2種類の行き止まり、最適ルートと遠回りルートの星判定、同点ルートでのゴースト表示
- 層B: 誤った確定でのミス加算と2通りのメッセージ、最後までの完走、クリア後の全地点確定、リセット
- 自動進行で Stage 1 層A から Stage 3 層B まで通しで遊べる。メニューから任意のステージ・層に移れる
- 波紋アニメーション中にタップ・リセット・ステージ切替をしても、例外や残像が出ない
- ステージ切替・モード切替のあとに前の状態が残らない
- C425でノードを指で確実に押せる。ダブルタップで拡大されない
