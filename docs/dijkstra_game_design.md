## 2. 配達員ダイクストラ 詳細設計

### 2.1 学習目標と対応する仕掛け

| # | 学習目標 | 体験させる場所 | 具体的な瞬間(MVPデータで確認済み) |
|---|---|---|---|
| 1 | 近い順に確定させる。未確定のうち札が最小の地点の値は覆らない | 層B | 札が最小でない地点を選ぶとミスになる |
| 2 | ラベルを更新する(緩和)。より近い行き方が見つかったら暫定値を書き換える | 層B | Stage 1 `D: 9→6`、Stage 2 `B: 13→8`、Stage 3 `D: 12→10`, `G: 16→14` |
| 3 | 直感が外れる。見た目に近い道が最短とは限らない | 層A | Stage 2の直線ルート(18)が最短(9)の2倍 |

目標2について、MVPでは緩和を自動で行い、メッセージで見せるだけにとどめる。プレイヤー自身に緩和させる「上級管制室」はPhase 2で検討する。

### 2.2 ゲームループ(2層構造)

#### 層A: 配達モード(直感で遊ぶ)

1. 地図に倉庫(S)とお届け先(G)が表示される。
2. プレイヤーは隣接する交差点を順にタップしてルートを作る。
3. Gに到達すると総コストが確定し、星(1〜3)が付く。
4. 最短ルートを「ゴースト」として重ねて表示し、等時線表示を解放する。

#### 層B: 管制室モード(アルゴリズムを手で実行する)

1. 各交差点に暫定所要時間の札を持たせる。初期値はSが0、他は∞とする。
2. プレイヤーは「未確定のうち札が最小の交差点」を選んで確定する。
3. ゲームは、確定した交差点から出る辺に沿って隣接交差点の札を自動で更新する。更新するのは値が小さくなる場合だけとする。
4. プレイヤーが誤った交差点を選ぶと、理由を示すメッセージを出す(3.6の判定表)。
5. Gが確定したらクリアとし、ミス回数と星を表示して等時線表示を解放する。
6. クリア後は「続けて全地点を確定」を選べる(採点対象外)。1回の実行で全地点への最短が求まることを体験させるための機能である。

ステージ内では、層A、結果とゴースト、層Bの順に進めることを推奨として画面に示す。ただしMVPでは、両層・全ステージとも自由に切り替えられる(ロックなし)。

プレイヤーが「終わる」ボタンを押すと、基盤のアンケート(3.8)を経てランチャーに戻る。

### 2.3 演出

| 演出 | 狙い | 表示タイミング |
|---|---|---|
| 波紋アニメーション(確定時に円が広がる) | 「近い順に確定する」を視覚化する | 層Bの確定時 |
| フロンティアの強調(暫定値を持つ未確定ノード) | 次の候補がどれかを示す | 層Bで常時 |
| 札の更新メッセージ(例: `A: ∞→4, B: ∞→3`) | 緩和の瞬間を印象づける | 層Bの確定時(1回の確定での更新をまとめて1行) |
| ゴーストルート(最短経路の点線) | 自分の解との差を実感させる | 層Aのクリア後 |
| 等時線ヒートマップ(全ノードを最短距離で色分け) | 1回の実行で全地点への最短が求まることに気づかせる | 各層のクリア後のみ(ネタバレ防止) |

### 2.4 ステージ構成(全体計画)

| Stage | 名称 | 内容 | 学べること | 時期 |
|---|---|---|---|---|
| 1 | 下町 | 10頂点未満、基本ルール | 基本 | MVP |
| 2 | 高速道路 | 遠回りだが速い道がある | 見た目の距離と重みは別物 | MVP |
| 3 | 一方通行 | 有向辺 | 有向グラフ | MVP |
| 4 | 通行料金 | 重みが料金 | 重みは時間でなくてよい | 未定 |
| 5 | 工事渋滞 | 途中で重みが変化 | 再計算 | 未定 |
| 6 | ボーナス道路 | 負の辺 | ダイクストラの限界、ベルマン–フォード | Phase 2 |
| 7 | 大都市 | 数百頂点 | 計算量の実感(アルゴリズムに任せる)| 未定 |
| 8 | 空港ラッシュ | 方向の手がかり | A*(ヒューリスティクス) | Phase 3 |

Stage 6は全体の山場になる。非負条件が崩れると「確定したはずの値が後から覆る」ことを見せ、その後にベルマン–フォード法を紹介する。

Stage 7は、スマホでは1頂点ずつタップできない。観戦(自動実行)とピンチ操作での拡大を前提に設計する。

### 2.5 採点

| 層 | ★3 | ★2 | ★1 |
|---|---|---|---|
| 層A | `cost == opt` | `cost <= star2`(ステージごとに定義)| それ以外 |
| 層B | ミス0 | ミス1〜2 | ミス3以上 |

- `star2` は、次善のルート程度なら★2になるよう、ステージデータで個別に指定する。一律に `opt × 1.25` とすると、Stage 2では次善(12)でも★1になり、ステージ間で難度がばらつくためである。
- ヒント③(答え)を使ったラウンドは★1が上限となる。ヒント①②は減点しない。
- ステージ・層ごとの最高の星を端末内に保存する(3.8)。

### 2.6 補助機能

#### ヒント(段階化、MVP)

| 段階 | 層A | 層B |
|---|---|---|
| ① | 現在地から進める交差点を光らせる | 候補(フロンティア)を光らせる |
| ② | 現在地からGへの最短で次に進む交差点を光らせる | 候補のうち札が最小のものを光らせる |
| ③ | 最短ルートを表示(★1上限)| 正解を1手自動で確定(★1上限)|

層Aのヒント②は「現在地から」の最短を示すので、プレイヤーがすでに遠回りしていても次善の一手を示せる。この一手は、Gからの逆向き最短距離(3.4の `distToGoal`)で求める。

#### 将来機能

- 制限: タップ数の上限や燃料制限を設け、闇雲な試行を防ぐ。
- 対決モード: CPU(アルゴリズム)と同時にスタートして競う。
- デイリーパズル: 日付をシードにしたランダムグラフを出題する。グラフは端末内で生成するので、サーバなしで全端末が同じ問題になる。
- エディタ解放: 全ステージをクリアすると、グラフ作成・出題機能が使えるようになる。

### 2.7 設計上の落とし穴と対策

| 問題 | 対策 |
|---|---|
| 小さいグラフは目視で解けてしまう | 「見た目は近いが重みが大きい」罠を意図的に配置する(Stage 2) |
| 同点の最短路があると採点が曖昧になる | 経路ではなくコストで判定し、最短ならどの経路でも正解とする(Stage 3は同点2経路) |
| 層Bで同値の候補が複数ある | どれを選んでも正解とする。ただし、教えたい緩和がタイ順に依存しないようデータを調整する(Stage 2のS-Aを4にした理由) |
| 層Aで行き止まりに入る | 進める交差点がなければ「行き止まりです。1手戻ってください」と表示する(例: Stage 1の `S-B-D-H-E`) |
| 負の辺の扱い | Stage 6でダイクストラの失敗を見せてからベルマン–フォードを導入する(実装上の注意は3.4) |
| 層Bで画面が混雑する | 小さいグラフから始め、ハイライトで視線を誘導する |
| 等時線・ゴーストを見ると答えが分かる | クリア後にのみ解放する |
| スマホでは地図が小さく、指で押しにくい | 縦画面では地図を縦長に描き、当たり判定を見た目より大きくする(3.7) |

## 3. 実装設計(ブラウザ版・基盤アプリ)

### 3.1 配布形態と技術選定

| 項目 | 方針 | 理由 |
|---|---|---|
| 配布 | 基盤のアプリ `dijkstra-delivery` として配信する(`http://<MacのIP>:3000/apps/dijkstra-delivery/`)| 端末へのインストールが不要で、PC・スマホのどちらからでも遊べる |
| サーバ処理 | なし(`server.py` を置かない) | 最短経路の計算時間は、MVPの9頂点なら一瞬、Stage 7(数百頂点)でも数ミリ秒で済む。基盤の方針「軽い処理は端末」に沿っており、読み込み後はMacが止まっても遊べる |
| 言語 | JavaScript(ESモジュール)。ビルドなし・外部ライブラリなし | `apps/` に置くだけで動くという基盤の利点を保つ。型はJSDocで補う |
| 描画 | SVG | `viewBox` で画面幅に合わせて拡大縮小できる。ノードごとにタップ判定を付けられる。状態の見た目をCSSで切り替えられる |
| 対象ブラウザ | iOS/iPadOS Safari、Android Chrome、PCのChrome・Safari・Edge(いずれも最新版) | 基盤の想定端末に合わせる |
| テスト | `node --test`(Nodeは開発時のみ必要) | ロジックをDOM非依存にしておけば、ブラウザなしで検証できる |

- 当初はtkinter版を想定していた。tkinterの画面はMac本体にしか出せず基盤のブラウザ配信に載らないため、取りやめた。
- LAN内のhttpはセキュアコンテキストではない(基盤 7章)。本作は `crypto`、クリップボード、Service Workerなどを使わないので影響を受けない。
- 基盤の規約5(計算の呼び出し口を `compute()` に集約し、重ければAPIに差し替える)は適用しない。最短経路計算をMacに移す予定がないためである。

### 3.3 データ構造

```js
/**
 * @typedef {{ u: string, v: string, w: number, directed?: boolean, kind?: "road" | "highway" }} Edge
 * @typedef {{
 *   id: string,                            // 進捗保存のキー。並べ替えや追加で変えない
 *   name: string, desc: string,
 *   nodes: Record<string, [number, number]>, // 名前 → 座標(viewBox 800×500 基準)
 *   edges: Edge[],
 *   expectedCost: number,                  // 設計値。テストで dijkstra() と照合する
 *   star2: number,                         // 層Aで★2となるコストの上限
 *   start?: string, goal?: string,         // 既定は "S" と "G"
 * }} Stage
 */
export const INF = Infinity;
// 隣接表: Map<u, Map<v, weight>>(無向辺は両方向を登録)
```

#### `validateStage(stage)`

テストで全ステージに適用し、次の条件をすべて満たすことを確かめる。

- 辺の端点、`start`、`goal` がすべて `nodes` に存在する。
- 同じ向きの辺が重複しない。重複すると隣接表で上書きされるためである。無向辺は両向きとして数える。
- 重みが正の整数である。負の辺はStage 6まで禁止する。
- `goal` が `start` から到達可能である。
- 座標がviewBoxの内側にある(余白30)。ノード間の距離が100以上ある(タップ判定の円 r=45 が重ならない)。辺が他のノードの上を通らない(ノード中心と辺の距離が30以上)。
- `id` がステージ間で重複しない。

### 3.4 コアロジック(`logic.js`)

```js
export function buildAdj(stage, { reverse = false, undirected = false } = {}) {
  const adj = new Map(Object.keys(stage.nodes).map((n) => [n, new Map()]));
  for (const e of stage.edges) {
    const [u, v] = reverse ? [e.v, e.u] : [e.u, e.v];
    adj.get(u).set(v, e.w);
    if (!e.directed || undirected) adj.get(v).set(u, e.w);
  }
  return adj;
}

// 確定集合を持つ O(V²) 版。数百頂点(Stage 7)まではこれで足りる
export function dijkstra(adj, s) {
  const dist = new Map([...adj.keys()].map((n) => [n, INF]));
  const prev = new Map();
  const done = new Set();
  dist.set(s, 0);
  for (;;) {
    let u = null;
    for (const [n, d] of dist) {
      if (!done.has(n) && d < INF && (u === null || d < dist.get(u))) u = n;
    }
    if (u === null) break;
    done.add(u);
    for (const [v, w] of adj.get(u)) {
      const nd = dist.get(u) + w;
      if (!done.has(v) && nd < dist.get(v)) {
        dist.set(v, nd);
        prev.set(v, u);
      }
    }
  }
  return { dist, prev };
}

/** s から g への経路。到達不能なら null */
export function pathTo(prev, s, g) {
  if (g !== s && !prev.has(g)) return null;
  const path = [g];
  while (path.at(-1) !== s) path.push(prev.get(path.at(-1)));
  return path.reverse();
}

/** 各ノードから goal への最短距離(層Aヒント②用)。辺を逆向きにして goal から解く */
export function distToGoal(stage) {
  return dijkstra(buildAdj(stage, { reverse: true }), stage.goal ?? "G").dist;
}
```

- ヒープは使わない。JSには標準の優先度キューがなく、この規模なら線形探索で十分に速い。
- 同じ距離の候補が複数あるときは、`nodes` の記述順で先にあるものを選ぶ。こうして結果を決定的にする。
- 負の辺についての注意(Phase 2): この `dijkstra()` は確定済みノードを再更新しないので、負の辺があると誤った答えを返す。Stage 6の失敗デモでは、この性質を `ControlRound`(3.5)で見せる。Stage 6の正解(`opt`)は `bellmanFord()` で求める。

### 3.5 ゲーム状態とモジュール設計

ラウンドの状態と判定はDOMに依存しないクラスに置く。画面側はその結果(種類と更新内容)を受け取り、描画と演出だけを行う。

#### `DeliveryRound`(層A、`logic.js`)

| 項目 | 内容 |
|---|---|
| 状態 | `route: string[]`、`finished: boolean`、`hintLevelUsed: number` |
| `tap(n) -> { kind, ... }` | `kind`: `added` / `undone` / `invalid` / `stuck`(追加後に進める交差点がない)/ `finished` |
| `undo()` | 1手戻る(ボタン用) |
| `cost()` / `stars()` | 2.5の採点 |

#### `ControlRound`(層B、`logic.js`)

| 項目 | 内容 |
|---|---|
| 状態 | `dist`(札)、`done: Set`、`prev`、`mistakes`、`finished`、`hintLevelUsed` |
| `candidates()` | 未確定かつ `dist` が有限のノード |
| `settle(n) -> { kind, updates }` | `kind`: `settled` / `already` / `unreached` / `not_min`。`settled` のとき `updates: {node, from, to}[]` |

`ControlRound` は確定集合を持つ教科書どおりのダイクストラ法なので、次の用途にもそのまま使える。

- 観戦モード(Phase 2): 「候補の最小を選んで `settle()`」を自動で繰り返すだけで実現できる。
- Stage 6の失敗デモ: 緩和によって確定済みノードの値が改善される場合、それを `violations` として記録して演出する。

#### `main.js`(画面の制御)

| 項目 | 内容 |
|---|---|
| 状態 | `stageIndex`、`mode`(`"A"` / `"B"`)、`opt`(`dist`・`prev`。ステージ読込時に計算)、`goalDist`(`distToGoal`)、`delivery`、`control`、`showHeat`、`hintNodes` |
| `loadStage()` / `reset()` | ラウンドを作り直し、演出レイヤーを空にする(実行中のアニメーションも消える) |
| 入力 | ノードの当たり判定円の `click`(マウス・タッチ共通)を、モードに応じたラウンドに渡す |
| `render()` | 状態に合わせてSVGの属性とメッセージ欄を更新する(`view.js`) |

#### `view.js`(描画)

- SVGは `<g>` で4層に分け、下から辺、ノード、文字(重み・札)、演出の順に重ねる。`render()` は演出層に触れないので、再描画しても波紋は消えない。
- 波紋は、演出層に円を追加し、CSSアニメーション(`transform: scale` と `opacity`)で広げ、`animationend` で削除する。
- 画面の向きが変わったら、座標変換だけを切り替えて描き直す(3.7)。ラウンドの状態はそのまま保つ。

### 3.6 各モードのルール実装

#### 層A(配達)

`DeliveryRound.tap(n)` は、タップされたノード `n` を次の順に判定する。

```
n == route[-2]                             → 1手戻る(undone)
n が route[-1] から辺で行ける未訪問ノード  → 追加(added)
    n == G                                 → 終了(finished)。星を計算
    n から行ける未訪問ノードがない         → stuck(「行き止まりです。1手戻ってください」)
それ以外                                   → invalid(「そこへは直接行けません」)
```

- 「辺で行ける」かどうかは、有向辺なら向きに従って判定する。
- ツールバーの「1手戻る」ボタンでも同じ操作ができる。
- 終了時には最短経路を点線(ゴースト)で重ねる。

#### 層B(管制室)

`ControlRound.settle(n)` は、選ばれたノード `n` を次の順に判定する。

```
m = min(dist[c] for c in candidates())
n が確定済み      → already  「確定済みです」            (ミスに数えない)
dist[n] == ∞      → unreached「まだ届いていません」       (ミスに数えない)
dist[n] > m       → not_min  「札が dist[n] より小さい候補が残っています」(ミス+1)
それ以外          → settled。出る辺を緩和し、更新を1行で表示
                    n が G なら finished
```

- 同値の候補が複数ある場合は、どれを選んでも正解とする。
- ミスに数えるのは、アルゴリズムの規則を誤解した選択(`not_min`)だけとする。`already` と `unreached` は押し間違いの可能性が高いため数えない。


- 縦長画面では座標のxとyを入れ替えて描く。対角線で反転するだけなので、グラフの形と距離関係は変わらない。幅390pxの端末でそのまま縮小すると地図は約390×244pxになるが、入れ替えると約390×624pxになる。

- 大きさはすべてviewBox単位で決める。縦長・幅390pxの場合、1単位はおよそ0.78pxになる。
  - ノードの半径は18とする。タップ判定には透明な円 r=45(約35px)を使い、指で押せる大きさ44px四方を上回るようにする。

- `touch-action: manipulation` でダブルタップによる拡大を止め、文字選択を無効にする。ホバーに頼る表示は作らない。
- 「等時線」ボタンはクリア前には無効(グレーアウト)にする。「1手戻る」ボタンは層Aでだけ有効にする。
- フォントはシステムフォント(`system-ui, "Hiragino Sans", "Noto Sans JP", sans-serif`)を使う。
- 色覚多様性に配慮し、ノードの状態は色に加えて枠線でも区別する。

| 層 | 状態 | 塗り | 枠 |
|---|---|---|---|
| 層B | 確定 | 青 | 太い実線 |
| 層B | 暫定値あり(候補) | 黄 | 破線 |
| 層B | 未到達 | 白 | 細い実線 |
| 層A | 選択ルート上 | 橙 | 太い実線 |

- 辺の重みは、辺の中点に白背景付きで表示する。有向辺は矢印で、高速道路はオレンジの太線で描く。
- 層Bでは、各ノードの上に札(暫定値)を表示する。

### 3.8 基盤との連携

| 項目 | 方針 |
|---|---|
| 進捗の保存 | localStorageの `dijkstra-delivery:progress` に `{ version: 1, stages: { [stageId]: { A: 星, B: 星 } } }` を保存する。読み書きは `try/catch` で囲み、保存できなくても遊べるようにする。端末内の保存で足り、Mac停止中も保存できるので、基盤の保存APIは使わない |
| `sdk.js` | `index.html` で `/core/sdk.js` を読み込み、`core-adapter.js` を経由してだけ使う。基盤なしで開発しているときや読み込みに失敗したときなど、sdkがない場合は何もしない。sdkのAPIが未確定なので、変更の影響をこのファイルに閉じ込める |
| 端末ID・ハートビート | sdkに任せる。アプリ側では何もしない |
| 利用の終了 | 「終わる」ボタンでsdkの終了処理(例: `core.finish()`)を呼ぶ。sdkがアンケートを出し、ランチャーへ戻す。sdkがなければ `/` へ移動する |
| Mac停止・Wi-Fi切断時(基盤の規約7) | 読み込み後は通信しないので遊び続けられる。「終わる」を押したときにアンケートの送信に失敗した場合は、sdkの再送に任せる |
| キャッシュ | 基盤が静的ファイルに `Cache-Control: no-cache` を付ける前提とする。付かない場合は更新後に古いJSが残るので、実際の挙動を確認する |

#### アンケート(`survey.json` の案、`version: 1`)

| # | 形式 | 設問 | 必須 |
|---|---|---|---|
| 1 | 段階評価 1〜5 | 管制室で「近い順に確定する」理由が分かった | 必須 |
| 2 | 段階評価 1〜5 | 配達で、見た目の近さと実際の所要時間が違うことに気づいた | 必須 |
| 3 | 単一選択 | いちばん難しかったステージ(下町 / 高速道路 / 一方通行 / どれも難しくなかった) | 任意 |
| 4 | 自由記述 | 分かりにくかったところ | 任意 |

設問1・2は、学習目標(2.1)の1と3にそれぞれ対応させている。

### 3.9 MVPステージデータ(検証済み)

座標はviewBox 800×500を基準とする。最適コスト、次善コスト、層Bの進行は、Pythonで書いたダイクストラ法と総当たり探索で確認した(2026-09-28)。どのステージもノード間の距離は160以上、辺とノードの距離は117以上ある。

#### Stage 1「下町」

`id: "downtown"`、無向グラフ。最適コストは13(`S-A-D-H-G`、唯一)、次善は16、`star2 = 16`。

- ノード: S(80,250) A(220,120) B(220,380) C(380,90) D(380,250) E(380,410) F(560,150) H(560,350) G(720,250)
- 辺: S-A 4, S-B 3, A-C 5, A-D 2, B-D 6, B-E 4, C-D 3, C-F 6, D-F 7, D-H 3, E-H 5, F-G 4, H-G 4
- 層Bの進行: S → B(3) → A(4, `D: 9→6`) → D(6) → E(7) → C/H(9) → F/G(13)

#### Stage 2「高速道路」

`id: "highway"`、無向グラフ。高速道路は遠回りに見えるが重みが小さい。最適コストは9(`S-P-Q-G`、唯一)、次善は12(`S-R-T-G`)、`star2 = 12`。

- ノード: S(80,250) A(250,250) B(450,250) G(720,250) P(250,90) Q(500,90) R(250,420) T(500,420)
- 辺(高速): S-P 3, P-Q 2, Q-G 4
- 辺(一般): S-A 4, A-B 9, B-G 5(直線ルートは合計18で、見た目では最も短く見える罠), P-A 4, Q-B 3, R-A 3, T-B 4, S-R 4, R-T 4, T-G 4
- 層Bの進行: S → P(3) → A/R(4, A確定で `B: ∞→13`) → Q(5, `B: 13→8`) → B/T(8) → G(9)
- 旧設計値からの変更: S-Aの重みを5から4にした。5のままだとAとQが同値(5)になり、Qを先に確定すると `B` の書き換えが起きない。4にするとAが必ず先に確定するので、緩和がタイ順に依存せずに見える。最適コストと経路は変わらない。

#### Stage 3「一方通行」

`id: "oneway"`、有向グラフ。最適コストは14(同点2経路: `S-A-C-E-G` と `S-B-C-E-G`)、次善は16、`star2 = 17`。

- ノード: S(80,250) A(240,130) B(240,370) C(420,250) D(600,130) E(600,370) G(740,250)
- 有向辺: S→A 3, S→B 5, A→C 4, B→C 2, C→D 3, C→E 5, D→G 6, E→G 2, A→D 9, B→A 1, E→D 1
- 層Bの進行: S → A(3) → B(5) → C(7, `D: 12→10`) → D(10) → E(12, `G: 16→14`) → G(14)
- 逆走できる場合の最適は12(`S-A-B-C-D-E-G`。B→AとE→Dを逆向きに使う)。一方通行によって結果が変わることの確認に使える。
- 同点の経路があるため、判定はコストの比較で行う。

### 3.10 テスト計画

#### 単体テスト

`node --test apps/dijkstra-delivery/tests/` で実行する。ブラウザは要らない。

- 全ステージで `validateStage()` が通る。
- 全ステージで、`dijkstra()` が求めた `goal` までの距離が `expectedCost` と一致する。
- Stage 3を `undirected: true` で解くと12、有向グラフとして解くと14になる(有向辺が逆向きに使われていない)。
- 到達不能ノードの `dist` が `INF` のまま残り、`pathTo()` が `null` を返す。
- `distToGoal()` が有向辺の向きを正しく反転している(Stage 3でAから11)。
- `ControlRound.settle()` の4分岐(`settled` / `already` / `unreached` / `not_min`)が正しく動き、ミスが `not_min` のときだけ増える。
- 3.9の「層Bの進行」どおりに `settle()` したとき、`updates` が記載どおりになる(Stage 2の `B: 13→8` など)。
- `ControlRound` を自動実行した結果が `dijkstra()` の結果と一致する。
- `DeliveryRound.tap()` の5分岐が正しく動く(Stage 1の `S-B-D-H-E` で `stuck`)。
- 星判定: 各ステージで最適、`star2` ちょうど、`star2 + 1` のコストを判定する。ヒント③使用時の★1上限も確認する。
- 進捗の読み書き: 壊れたJSONや未知の `version` を読んでも例外にならない。

#### 手動テスト

PCのChrome・Safari、iPhoneのSafari、AndroidのChromeで確認する。

- 層A: 通れない辺のタップ、1手戻し(タップ・ボタンの両方)、行き止まり、最適ルートと遠回りルートの星判定
- 層B: 誤った確定でのミス加算、最後までの完走、クリア後の全地点確定、リセット
- 波紋アニメーション中にタップ・リセット・ステージ切替をしても、例外や残像が出ない
- ステージ切替・モード切替のあとに前の状態が残らない
- ラウンドの途中で画面の向きを変えても状態が保たれ、縦横それぞれで正しく描き直される
- スマホでノードを指で確実に押せる。ダブルタップで拡大されない
- 基盤なし(静的サーバのみ)で遊べる。基盤上では「終わる」でアンケートが出て、ランチャーに戻る
- 読み込み後にMacを止めても遊び続けられる。再読み込み後も星の記録が残っている

## 6. 引継ぎ時の最初の作業

本作は基盤の骨組みより先に着手できる。本作は、基盤の次のアクション2にある「計算APIを持たないサンプルアプリ」も兼ねる。

1. `apps/dijkstra-delivery/` に3.2の骨組み(`app.json`、`package.json`、`static/index.html`)を作る。
2. `logic.js` と `stages.js` に、3.3〜3.5のロジックと3.9のステージデータを書く。3.10の単体テストを `node --test` で通す。
3. `view.js` と `main.js` で、層A、層B、演出(波紋・等時線)、縦長画面の順に画面を作る。動作確認は `python3 -m http.server --bind 0.0.0.0 -d apps/dijkstra-delivery/static` で配信して行い、同じLANのスマホからも開く(ESモジュールは `file://` では読み込めない)。
4. 基盤ができたら `core-adapter.js` をsdkに接続し、`survey.json` を置いてアンケートまで確認する。
5. 受け入れ基準(3.11)を満たしたら、Phase 2に進む。
