## 2. 配達員ダイクストラ 詳細設計

### 2.1 学習目標と対応する仕掛け

| # | 学習目標 | 体験させる場所 | 具体的な瞬間(MVPデータで確認済み) |
|---|---|---|---|
| 1 | **近い順に確定させる**: 未確定のうち札が最小の地点の値は覆らない | 層B | 札が最小でない地点を選ぶとミスになる |
| 2 | **ラベルの更新(緩和)**: より近い行き方が見つかったら暫定値を書き換える | 層B | Stage 1 `D: 9→6`、Stage 2 `B: 13→8`、Stage 3 `D: 12→10`, `G: 16→14` |
| 3 | **直感が外れる**: 見た目に近い道が最短とは限らない | 層A | Stage 2 の直線ルート(18)が最短(9)の2倍 |

目標2は、MVPでは緩和を自動で行いメッセージで見せる(受動的)。プレイヤー自身に緩和させる「上級管制室」は Phase 2 で検討する。

### 2.2 ゲームループ(2層構造)

**層A:配達モード(直感で遊ぶ)**
1. 地図に倉庫(S)とお届け先(G)が表示される
2. プレイヤーが隣接する交差点を順にタップしてルートを作る
3. Gに到達すると総コストが確定し、星(1〜3)が付く
4. 最短ルートを「ゴースト」として重ねて表示し、等時線表示を解放する

**層B:管制室モード(アルゴリズムを手で実行する)**
1. 各交差点に暫定所要時間の札を持たせる(初期値: Sが0、他は∞)
2. 「未確定のうち札が最小の交差点」を選んで確定する
3. 確定した交差点から出る辺に沿って、隣接交差点の札を自動で更新する(小さくなる場合のみ)
4. 誤った交差点を選ぶと理由を示すメッセージを出す(3.6 の判定表)
5. Gが確定したらクリア。ミス回数と星を表示し、等時線表示を解放する
6. クリア後は「続けて全地点を確定」を選べる(採点対象外)。1回の実行で全地点の最短が求まることを体験させる

**ステージ内の進行**: 層A → 結果とゴースト → 層B の順を推奨として画面に示す。MVPでは両層・全ステージとも自由に切り替えられる(ロックなし)。

**利用の終了**: 「終わる」ボタンで基盤のアンケート(3.8)を経てランチャーに戻る。

### 2.3 演出

| 演出 | 狙い | 表示タイミング |
|---|---|---|
| 波紋アニメーション(確定時に円が広がる) | 「近い順に確定する」を視覚化 | 層Bの確定時 |
| フロンティアの強調(暫定値を持つ未確定ノード) | 次の候補が何かを示す | 層B 常時 |
| 札の更新メッセージ(例: `A: ∞→4, B: ∞→3`) | 緩和の瞬間を印象づける | 層Bの確定時(1回の確定での更新をまとめて1行) |
| ゴーストルート(最短経路の点線) | 自分の解との差を実感 | 層Aのクリア後 |
| 等時線ヒートマップ(全ノードを最短距離で色分け) | 1回の実行で全地点への最短が求まる事実に気づく | 各層のクリア後のみ(ネタバレ防止) |

### 2.4 ステージ構成(全体計画)

| Stage | 名称 | 内容 | 学べること | 時期 |
|---|---|---|---|---|
| 1 | 下町 | 10頂点未満、基本ルール | 基本 | MVP |
| 2 | 高速道路 | 遠回りだが速い道がある | 見た目の距離と重みは別物 | MVP |
| 3 | 一方通行 | 有向辺 | 有向グラフ | MVP |
| 4 | 通行料金 | 重みが料金 | 重みは時間でなくてよい | 未定 |
| 5 | 工事渋滞 | 途中で重みが変化 | 再計算 | 未定 |
| 6 | ボーナス道路 | 負の辺 | ダイクストラの限界、ベルマン–フォード | Phase 2 |
| 7 | 大都市 | 数百頂点 | 計算量の実感(アルゴリズムに任せる)| 未定 |
| 8 | 空港ラッシュ | 方向の手がかり | A*(ヒューリスティクス) | Phase 3 |

Stage 6 は山場: 非負条件が崩れると「確定したはずの値が後から覆る」ことを見せ、その後にベルマン–フォード法を紹介する。

Stage 7 はスマホでは1頂点ずつタップできない。観戦(自動実行)とピンチ操作での拡大を前提に設計する。

### 2.5 採点

| 層 | ★3 | ★2 | ★1 |
|---|---|---|---|
| 層A | `cost == opt` | `cost <= star2`(ステージごとに定義)| それ以外 |
| 層B | ミス0 | ミス1〜2 | ミス3以上 |

- `star2` は「次善のルート程度なら★2」になるようステージデータで個別に指定する。一律 `opt × 1.25` にすると、Stage 2 では次善(12)でも★1になり、ステージ間で難度がぶれるため。
- ヒント③(答え)を使ったラウンドは★1が上限。①②は減点しない。
- ステージ・層ごとの最高の星を端末内に保存する(3.8)。

### 2.6 補助機能

**ヒント(段階化、MVP)**

| 段階 | 層A | 層B |
|---|---|---|
| ① | 現在地から進める交差点を光らせる | 候補(フロンティア)を光らせる |
| ② | 現在地からGへの最短で次に進む交差点を光らせる | 候補のうち札が最小のものを光らせる |
| ③ | 最短ルートを表示(★1上限)| 正解を1手自動で確定(★1上限)|

層Aの②は「現在地から」の最短なので、既に遠回りしていても次善の一手を示せる。Gからの逆向き最短距離(3.4 の `distToGoal`)で求める。

**将来機能**
- 制限: タップ数上限や燃料制限で闇雲な試行を防ぐ
- 対決モード: CPU(アルゴリズム)と同時スタートで競う
- デイリーパズル: 日付をシードにしたランダムグラフ。端末内で生成するので、サーバなしで全端末が同じ問題になる
- エディタ解放: 全ステージクリアでグラフ作成・出題機能

### 2.7 設計上の落とし穴と対策
| 問題 | 対策 |
|---|---|
| 小さいグラフは目視で解けてしまう | 「見た目は近いが重みが大きい」罠を意図的に配置(Stage 2) |
| 同点の最短路があり採点が曖昧 | **経路ではなくコストで判定**し、「最短ならどれでも正解」とする(Stage 3 は同点2経路) |
| 層Bで同値の候補が複数ある | どれを選んでも正解。ただし教えたい緩和はタイ順に依存しないようデータを調整する(Stage 2 の S-A を 4 にした理由) |
| 層Aで行き止まりに入る | 進める交差点がなければ「行き止まりです。1手戻ってください」と表示(例: Stage 1 の `S-B-D-H-E`) |
| 負の辺の扱い | Stage 6でダイクストラの失敗を見せてからベルマン–フォードを導入(実装上の注意は 3.4) |
| 層Bで画面が混む | 小さいグラフから開始、ハイライトで視線誘導 |
| 等時線・ゴーストが答えを明かす | クリア後にのみ解放 |
| スマホでは地図が小さく、指で押しにくい | 縦画面では地図を縦長に描き、当たり判定を見た目より大きくする(3.7) |

## 3. 実装設計(ブラウザ版・基盤アプリ)

### 3.1 配布形態と技術選定

| 項目 | 方針 | 理由 |
|---|---|---|
| 配布 | 基盤のアプリ `dijkstra-delivery` として配信(`http://<MacのIP>:3000/apps/dijkstra-delivery/`)| 端末にインストール不要で、PC・スマホのどちらからでも遊べる |
| サーバ処理 | なし(`server.py` を置かない) | 最短経路計算は MVP の9頂点で一瞬、Stage 7(数百頂点)でも数ミリ秒。基盤の方針「軽い処理は端末」に沿い、読込後は Mac が止まっても遊べる |
| 言語 | JavaScript(ES モジュール)。ビルドなし・外部ライブラリなし | `apps/` に置くだけで動くという基盤の利点を保つ。型は JSDoc で補う |
| 描画 | SVG | `viewBox` で画面幅に合わせて拡大縮小できる。ノードごとにタップ判定を付けられる。状態の見た目を CSS で切り替えられる |
| 対象ブラウザ | iOS/iPadOS Safari、Android Chrome、PC の Chrome・Safari・Edge(いずれも最新版) | 基盤の想定端末 |
| テスト | `node --test`(Node は開発時のみ必要) | ロジックを DOM 非依存にしておけばブラウザなしで検証できる |

- 当初は tkinter 版を想定していたが、基盤のブラウザ配信に載らない(Mac 本体の画面にしか出せない)ため取りやめた。
- LAN 内の http はセキュアコンテキストではない(基盤 7章)。本作は `crypto`・クリップボード・Service Worker などを使わないので影響しない。
- 基盤の規約5(計算の呼び出し口を `compute()` に集約し、重ければ API に差し替える)は適用しない。最短経路計算を Mac に移す予定がないため。

### 3.3 データ構造

```js
/**
 * @typedef {{ u: string, v: string, w: number, directed?: boolean, kind?: "road" | "highway" }} Edge
 * @typedef {{
 *   id: string,                            // 進捗保存のキー。並べ替えや追加で変えない
 *   name: string, desc: string,
 *   nodes: Record<string, [number, number]>, // 名前 → 座標(viewBox 800×500 基準)
 *   edges: Edge[],
 *   expectedCost: number,                  // 設計値。テストで dijkstra() と照合する
 *   star2: number,                         // 層Aで★2となるコストの上限
 *   start?: string, goal?: string,         // 既定は "S" と "G"
 * }} Stage
 */
export const INF = Infinity;
// 隣接表: Map<u, Map<v, weight>>(無向辺は両方向を登録)
```

**`validateStage(stage)`**(テストで全ステージに適用)
- 辺の端点・start・goal がすべて `nodes` に存在する
- 同じ向きの辺が重複しない(隣接表で上書きされるのを防ぐ)。無向辺は両向きとして数える
- 重みが正の整数(負の辺は Stage 6 まで禁止)
- goal が start から到達可能
- 座標が viewBox 内(余白 30)、ノード間距離が 100 以上(タップ判定の円 r=45 が重ならない)、辺が他ノードの上を通らない(ノード中心と辺の距離が 30 以上)
- `id` がステージ間で重複しない

### 3.4 コアロジック(`logic.js`)

```js
export function buildAdj(stage, { reverse = false, undirected = false } = {}) {
  const adj = new Map(Object.keys(stage.nodes).map((n) => [n, new Map()]));
  for (const e of stage.edges) {
    const [u, v] = reverse ? [e.v, e.u] : [e.u, e.v];
    adj.get(u).set(v, e.w);
    if (!e.directed || undirected) adj.get(v).set(u, e.w);
  }
  return adj;
}

// 確定集合を持つ O(V²) 版。数百頂点(Stage 7)まではこれで足りる
export function dijkstra(adj, s) {
  const dist = new Map([...adj.keys()].map((n) => [n, INF]));
  const prev = new Map();
  const done = new Set();
  dist.set(s, 0);
  for (;;) {
    let u = null;
    for (const [n, d] of dist) {
      if (!done.has(n) && d < INF && (u === null || d < dist.get(u))) u = n;
    }
    if (u === null) break;
    done.add(u);
    for (const [v, w] of adj.get(u)) {
      const nd = dist.get(u) + w;
      if (!done.has(v) && nd < dist.get(v)) {
        dist.set(v, nd);
        prev.set(v, u);
      }
    }
  }
  return { dist, prev };
}

/** s から g への経路。到達不能なら null */
export function pathTo(prev, s, g) {
  if (g !== s && !prev.has(g)) return null;
  const path = [g];
  while (path.at(-1) !== s) path.push(prev.get(path.at(-1)));
  return path.reverse();
}

/** 各ノードから goal への最短距離(層Aヒント②用)。辺を逆向きにして goal から解く */
export function distToGoal(stage) {
  return dijkstra(buildAdj(stage, { reverse: true }), stage.goal ?? "G").dist;
}
```

- ヒープは使わない。JS には標準の優先度キューがなく、この規模では線形探索で十分に速い。
- 同じ距離の候補は `nodes` の記述順で先のものを選ぶ(結果を決定的にする)。
- **負の辺についての注意(Phase 2)**: この `dijkstra()` は確定済みノードを再更新しないので、負の辺があると誤った答えを返す。Stage 6 の失敗デモはこの性質を `ControlRound`(3.5)で見せる。Stage 6 の正解(`opt`)は `bellmanFord()` で求める。

### 3.5 ゲーム状態とモジュール設計

ラウンドの状態と判定は DOM 非依存のクラスに置き、画面はその結果(種類と更新内容)を受けて描画・演出だけを行う。

**`DeliveryRound`(層A、`logic.js`)**

| 項目 | 内容 |
|---|---|
| 状態 | `route: string[]`、`finished: boolean`、`hintLevelUsed: number` |
| `tap(n) -> { kind, ... }` | `kind`: `added` / `undone` / `invalid` / `stuck`(追加後に進める交差点がない)/ `finished` |
| `undo()` | 1手戻る(ボタン用) |
| `cost()` / `stars()` | 2.5 の採点 |

**`ControlRound`(層B、`logic.js`)**

| 項目 | 内容 |
|---|---|
| 状態 | `dist`(札)、`done: Set`、`prev`、`mistakes`、`finished`、`hintLevelUsed` |
| `candidates()` | 未確定かつ `dist` が有限のノード |
| `settle(n) -> { kind, updates }` | `kind`: `settled` / `already` / `unreached` / `not_min`。`settled` のとき `updates: {node, from, to}[]` |

`ControlRound` は確定集合を持つ教科書どおりのダイクストラ法なので、次の用途にそのまま使える。
- 観戦モード(Phase 2): 「候補の最小を選んで `settle()`」を自動で繰り返すだけ
- Stage 6 の失敗デモ: 緩和で確定済みノードの値が改善される場合に `violations` として記録し、演出する

**`main.js`(画面の制御)**

| 項目 | 内容 |
|---|---|
| 状態 | `stageIndex`、`mode`(`"A"` / `"B"`)、`opt`(`dist`・`prev`。ステージ読込時に計算)、`goalDist`(`distToGoal`)、`delivery`、`control`、`showHeat`、`hintNodes` |
| `loadStage()` / `reset()` | ラウンドを作り直し、演出レイヤーを空にする(実行中のアニメーションも消える) |
| 入力 | ノードの当たり判定円の `click`(マウス・タッチ共通)をモード別のラウンドに渡す |
| `render()` | 状態から SVG の属性とメッセージ欄を更新する(`view.js`) |

**`view.js`(描画)**
- SVG を `<g>` で4層に分ける: 辺 → ノード → 文字(重み・札)→ 演出。`render()` は演出層に触れないので、再描画で波紋が消えない。
- 波紋は演出層に円を追加し、CSS アニメーション(`transform: scale` と `opacity`)で広げ、`animationend` で削除する。
- 画面の向きが変わったら座標変換だけ切り替えて描き直す(3.7)。ラウンドの状態は保たれる。

### 3.6 各モードのルール実装

**層A(配達)** — `DeliveryRound.tap(n)` の判定:
```
n == route[-2]                             → 1手戻る(undone)
n が route[-1] から辺で行ける未訪問ノード  → 追加(added)
    n == G                                 → 終了(finished)。星を計算
    n から行ける未訪問ノードがない         → stuck(「行き止まりです。1手戻ってください」)
それ以外                                   → invalid(「そこへは直接行けません」)
```
- 「辺で行ける」は有向辺なら向きに従う
- ツールバーの「1手戻る」ボタンでも同じ操作ができる
- 終了時に最短経路を点線(ゴースト)で重ねる

**層B(管制室)** — `ControlRound.settle(n)` の判定:
```
m = min(dist[c] for c in candidates())
n が確定済み      → already  「確定済みです」            (ミスに数えない)
dist[n] == ∞      → unreached「まだ届いていません」       (ミスに数えない)
dist[n] > m       → not_min  「札が dist[n] より小さい候補が残っています」(ミス+1)
それ以外          → settled。出る辺を緩和し、更新を1行で表示
                    n が G なら finished
```
- 同値の候補が複数ある場合はどれを選んでも正解
- ミスに数えるのは「アルゴリズムの規則を誤解した選択」(`not_min`)だけとする。`already` と `unreached` は押し間違いの可能性が高いため

### 3.8 基盤との連携

| 項目 | 方針 |
|---|---|
| 進捗の保存 | localStorage の `dijkstra-delivery:progress` に `{ version: 1, stages: { [stageId]: { A: 星, B: 星 } } }` を保存する。読み書きは `try/catch` で囲み、保存できなくても遊べるようにする。基盤の保存APIは使わない(端末内で足り、Mac 停止中も保存できるため) |
| `sdk.js` | `index.html` で `/core/sdk.js` を読み、`core-adapter.js` 経由でだけ使う。sdk がない(基盤なしの開発時・読込失敗)ときは何もしない。sdk の API が未確定なので、影響をこのファイルに閉じ込める |
| 端末ID・ハートビート | sdk に任せる。アプリは何もしない |
| 利用の終了 | 「終わる」ボタンで sdk の終了処理(例: `core.finish()`)を呼ぶ。sdk がアンケートを出し、ランチャーへ戻す。sdk がなければ `/` へ移動する |
| Mac 停止・Wi-Fi 切断時(基盤の規約7) | 読込後は通信しないので遊び続けられる。「終わる」でアンケートの送信に失敗した場合は sdk の再送に任せる |
| キャッシュ | 基盤が静的ファイルに `Cache-Control: no-cache` を付ける前提。付かない場合は更新後に古い JS が残るので確認する |

### 3.10 テスト計画

**単体テスト(`node --test apps/dijkstra-delivery/tests/`、ブラウザ不要)**
- 全ステージで `validateStage()` が通る
- 全ステージで `dijkstra()` の goal までの距離が `expectedCost` と一致する
- Stage 3 を `undirected: true` で解くと 12、有向として解くと 14(有向辺が逆向きに使われない)
- 到達不能ノードの `dist` が `INF` のままで、`pathTo()` が `null` を返す
- `distToGoal()` が有向辺の向きを正しく反転している(Stage 3 で A から 11)
- `ControlRound.settle()` の4分岐(`settled` / `already` / `unreached` / `not_min`)と、ミスが `not_min` のときだけ増えること
- 3.9 の「層Bの進行」どおりに `settle()` したときの `updates` が記載どおりになる(Stage 2 の `B: 13→8` など)
- `ControlRound` を自動実行した結果が `dijkstra()` と一致する
- `DeliveryRound.tap()` の5分岐(Stage 1 の `S-B-D-H-E` で `stuck`)
- 星判定: 各ステージの最適・`star2` ちょうど・`star2 + 1`、ヒント③使用時の★1上限
- 進捗の読み書き: 壊れた JSON や未知の `version` を読んでも例外にならない

**手動テスト**(PC の Chrome・Safari、iPhone の Safari、Android の Chrome)
- 層A: 通れない辺のタップ、1手戻し(タップ・ボタン両方)、行き止まり、最適ルート・遠回りルートの星判定
- 層B: 誤った確定でミス加算、最後までの完走、クリア後の全地点確定、リセット
- 波紋アニメーション中のタップ・リセット・ステージ切替で例外や残像が出ない
- ステージ切替・モード切替で状態が残らない
- ラウンドの途中で画面の向きを変えても状態が保たれ、縦横で正しく描き直される
- スマホでノードを指で確実に押せる。ダブルタップで拡大されない
- 基盤なし(静的サーバのみ)で遊べる。基盤上では「終わる」でアンケートが出てランチャーに戻る
- 読込後に Mac を止めても遊び続けられる。再読込後も星の記録が残る

## 5. 未決事項・リスク

- **sdk.js の API**: 基盤側で未確定(セッション開始・終了処理の名前や呼び方)。`core-adapter.js` に閉じ込めているので、決まったらそこだけ直す。
- **プレイ結果の集計**: アンケートの回答にはセッションの長さしか残らず、星やミス数は Mac に届かない。学習効果を結果と照らし合わせたいなら、基盤に「終了処理にアプリ独自の値(例: `{stars, mistakes}`)を添えて回答と一緒に保存する」機能を求める必要がある。MVP では扱わない。
- **端末内データの消失**: iPhone/iPad の Safari はしばらく使わないサイトの保存データを消すことがあり、星の記録も消える(基盤 7章)。星だけなので MVP では受け入れる。
- **見た目のテイスト**: ポップな街並みか、ミニマルな図解風か(未決定)。
- **負の辺の見せ方**: `ControlRound` の `violations` をどう演出するか(Phase 2 で設計)。
- **グラフの自動生成**: 手作りステージは3つのみ。ランダム生成(ドロネー三角形分割等)は Phase 3。生成したグラフにも `validateStage()` と「教えたい緩和がタイ順に依存しない」条件を課す。
