# システム基盤 要件整理(引き継ぎ用)

最終更新: 2026-09-28

## 1. 目的・スコープ

同一LAN内の複数端末のブラウザから、Mac(M4)上の複数のアプリを使えるようにする基盤を定める。アプリの内容は別途検討しており、この文書では扱わない。

### 基盤とアプリの境界

| 基盤が決める・提供するもの | アプリに任せるもの |
|---|---|
| サーバ、URL設計、アプリの配置規約 | 画面、操作、アプリ内のロジック |
| 端末ID、サーバ側保存、監視・ログ | 保存するデータの中身 |
| アンケートの表示・送信・集計の仕組み | 設問の内容、アンケートを出すタイミング |
| 計算APIを載せる仕組みと実装ルール | 計算の中身、どの処理をMacに置くかの判断 |
| クライアントSDK(`/core/sdk.js`) | SDKを使ったアプリ固有の処理 |

**当面の対象外:** 宅外アクセス、ユーザ認証、端末をまたいだデータの共有、リアルタイム通信(WebSocket)、PWA化、RL推論。

用語: 「端末」は利用するクライアント機器(PC・スマホ・タブレット)、「Mac」はサーバ機、「アプリ」は基盤に載せる個々のWebアプリを指す。

## 2. 前提

| 項目 | 内容 |
|---|---|
| サーバ | Mac(M4)1台 |
| ネットワーク | 同一LANのみ。宅外からはアクセスしない |
| アクセス制御 | 一般向けの画面・APIは、LAN内の機器なら誰でも接続できる。管理画面はMac本体からのみ開ける |
| アプリ | 複数。ランチャー画面から選んで起動する |
| 言語 | サーバ側はPython(FastAPI / uvicorn) |
| データ | 端末内保存と、Macでの端末ID単位の保存を併用する。端末をまたいでは共有しない |
| 処理の分担 | 軽い処理は端末、重い処理だけMacの計算APIに置く。どこで分けるかはアプリごとに判断する |

## 3. 全体構成

Mac上で、一般向けサーバと管理サーバの2つのプロセスを動かす。

```
[端末ブラウザ]                         [一般向けサーバ 0.0.0.0:3000]
  ランチャー / 各アプリの画面   ──HTTP──>   /               ランチャー
  sdk.js(端末ID・API呼び出し)             /apps/<app>/    各アプリの静的ファイル
  端末内保存(localStorage等)              /api/<app>/*    各アプリの計算API(状態なし)
                                          /api/core/*     基盤API(保存・アンケート回答・端末・ヘルスチェック)
                                              │ 書き込み
                                          data/  storage.db / metrics.db / logs
                                              │ 読み取り専用
[Mac本体のブラウザ]           ──HTTP──>   [管理サーバ 127.0.0.1:3001]
                                          監視画面・アンケート集計・CSV出力
```

### URL設計

**一般向けサーバ(`http://<MacのIP>:3000`)**

| パス | 内容 |
|---|---|
| `/` | ランチャー。`apps/` 配下のアプリを一覧表示する |
| `/apps/<app>/` | アプリの静的ファイル |
| `/api/<app>/*` | アプリの計算API |
| `/api/core/storage/<app>/<key>` | 保存API(GET / PUT / DELETE) |
| `/api/core/surveys/<app>` | アンケート定義の取得(GET)、回答の送信(POST) |
| `/api/core/devices` | 端末情報の登録・更新 |
| `/api/core/health` | ヘルスチェック |
| `/core/*` | 基盤の静的ファイル(`sdk.js` など) |

すべて同一オリジン(同じホスト・ポート)から配信するため、CORSは不要。

**管理サーバ(`http://localhost:3001`)**

| パス | 内容 |
|---|---|
| `/` | 監視画面(4.4) |
| `/surveys` | アンケート集計とCSVダウンロード(4.6) |

管理サーバの詳細は4.7に記載する。

### ディレクトリ構成

```
akabane2026/
  core/              基盤のPythonコード(起動、アプリ読み込み、保存、監視)
    main.py          一般向けサーバ
    admin.py         管理サーバ
    static/          ランチャー、sdk.js
    admin_static/    監視画面、アンケート集計画面
  apps/
    <app>/
      app.json       表示名・説明など(ランチャー用)
      survey.json    任意。アンケートを実施する場合のみ
      static/        index.html ほか
      server.py      任意。計算APIを持つ場合のみ
  data/              storage.db(保存データ・アンケート回答)、metrics.db、ログ
                     (バックアップ対象は storage.db)
```

- 基盤のパッケージ名に `platform` は使わない。Python標準ライブラリの `platform` モジュールと衝突するため。

## 4. 基盤の機能

### 4.1 端末ID

- 初回アクセス時に `sdk.js` が `crypto.getRandomValues()` で128bitの乱数を生成し、localStorageに保存する。LAN内のhttpでは `crypto.randomUUID()` が使えないため、この方法にする。
- すべてのAPI呼び出しに `X-Device-Id` ヘッダで付ける。
- 端末IDは識別用であり、認証ではない。LAN内の誰でも他の端末のIDを名乗れる。
- 初回アクセス時に `/api/core/devices` へUser-Agentと表示名(任意)を送り、監視画面で端末を見分けられるようにする。

### 4.2 計算API

- アプリの `server.py` が公開する `APIRouter` を、基盤が `/api/<app>` 配下に登録する。
- 状態を持たない。状態が必要なら、端末が保持してリクエストに含めて送る。
- 入出力はJSONとし、Pydanticモデルでスキーマを定義する。
- 重い処理は `def` で書く(7章)。

### 4.3 保存API

- 基盤の中で状態を持つのは、保存APIとアンケート回答(4.6)だけとする。
- SQLite(`data/storage.db`)に、(アプリ名, 端末ID, キー) を主キーとしてJSON値を保存する。
- 値のサイズに上限を設ける(仮に1件1MB)。
- SQLiteはWALモードで使い、接続はリクエストごとに開く(スレッド間で共有しない)。
- バックアップは、SQLiteのオンラインバックアップ(`sqlite3 storage.db ".backup ..."`)を `launchd` で定期実行する。書き込み中のファイルを単純にコピーすると壊れることがある。

### 4.4 監視・ログ

- ミドルウェアで全リクエストを記録する(時刻、端末ID、アプリ名、パス、ステータス、処理時間)。
  - 記録はSQLite(`data/metrics.db`)に保存し、保持期間を過ぎたものは削除する。複数ワーカーでも集計できるよう、メモリ上には持たない。
  - アプリケーションログはJSON形式で、ローテーション付きでファイルに出す。
- 管理サーバの監視画面で次の情報を確認できる。閲覧専用とし、データの削除などの操作は置かない。
  - 接続中の端末(直近5分以内にリクエストかハートビートがあった端末)
  - アプリ・APIごとの呼び出し数と応答時間
  - エラーの一覧
- `sdk.js` は、画面が表示されている間、1分に1回ハートビートを送る。
- `/api/core/health` は、監視や `launchd` 運用の死活確認に使う。

### 4.5 クライアントSDK(`/core/sdk.js`)

アプリごとに作り直さなくて済むよう、次の機能を提供する。

- 端末IDの生成・取得
- API呼び出し(`X-Device-Id` の付与、タイムアウト、失敗時のエラーの統一)
- 保存APIの読み書き
- ハートビート
- セッションの開始・終了と、終了時のアンケート表示(4.6)

### 4.6 アンケート

アプリの利用を終えた端末に任意回答のアンケートを出し、回答をMacに集める。

**実施の流れ**

1. アプリの起動時に、`sdk.js` がセッションIDを発行する(1回の利用を1セッションとする)。
2. アプリは終了時に `sdk.js` の終了処理(例: `core.finish()`)を呼ぶ。ブラウザのタブを閉じる操作は確実に検知できないため、終了はアプリが明示的に知らせる。
3. `survey.json` があるアプリでは、`sdk.js` がアンケート画面を重ねて表示する。
4. 回答すると送信してランチャーに戻る。「スキップ」を選ぶと、送信せずにランチャーに戻る。

**アンケート定義(`apps/<app>/survey.json`)**

- 設問の形式は、単一選択、複数選択、段階評価(例: 1〜5)、自由記述の4種類とする。
- 設問ごとに必須・任意を指定できる。アンケート全体はスキップできる。
- 定義には `version` を持たせる。設問を変えたら上げ、回答に記録して、どの版への回答かを区別する。
- 表示は `sdk.js` の共通画面で行う。アプリは設問を書くだけでよい。

**回答の保存**

- `storage.db` の専用テーブルに保存する。保存データと同じくバックアップの対象にする。
- 1件の回答に、アプリ名、定義の `version`、セッションID、端末ID、回答日時、セッションの長さ、各設問の回答を記録する。
- 送信に失敗した回答は端末内に保存し、次にアクセスしたときに再送する。二重登録はセッションIDで防ぐ。
- 自由記述には文字数の上限を設ける(仮に1問1000文字)。

**集計**

- 管理サーバの集計画面で、アプリ・版ごとの回答数、選択式設問の集計、自由記述の一覧を見られる。
- アプリ・版ごとにCSVでダウンロードできる。詳しい分析はCSVを使って基盤の外で行う。
- 一般向けサーバには、回答を読み出すAPIを置かない(送信のみ)。

### 4.7 管理サーバ

監視画面とアンケート集計は、一般向けサーバとは別のプロセス(管理サーバ)で提供し、Mac本体からしか接続できないようにする。

- `127.0.0.1:3001` で待ち受ける。LAN上の他の機器からは接続する経路がないため、パスワードなどの認証は置かない。
  - **`0.0.0.0` に変えてはならない。** 変えると、LAN内の誰でも管理画面を開ける状態になる。
- Mac本体のブラウザで `http://localhost:3001` を開いて使う。
- 別のPCから見る場合は、Macの「リモートログイン」(SSH)を有効にしたうえで、SSHのポート転送を使う。
  ```
  ssh -L 3001:localhost:3001 <ユーザ名>@<MacのIP>
  ```
  接続後、そのPCのブラウザで `http://localhost:3001` を開く。
- `storage.db` と `metrics.db` は、読み取り専用モード(`file:...?mode=ro`)で開く。書き込みは一般向けサーバだけが行う。
- 一般向けサーバとは別の `launchd` ジョブとして常駐させる。管理サーバが止まっても、一般向けサーバには影響しない。

## 5. アプリ組み込み規約

1. アプリ名は `[a-z0-9-]+` とする。`core` は予約語とする。
2. `apps/<app>/` にディレクトリを置けば、再起動時にランチャーと配信に反映される。
3. `server.py` は任意。置く場合は `router = APIRouter()` を公開する。
4. localStorage・IndexedDBは全アプリで共有される(同一オリジンのため)。キーとDB名は `<app>:` で始める。
5. 計算の呼び出し口は `compute()` のような1関数に集約する。最初は端末内で実行し、重ければ中身をAPI呼び出しに差し替える。差し替えで呼び出し側が変わらないよう、最初から `async`(Promiseを返す)にしておく。
6. APIは必要なタイミングだけ呼ぶ(毎フレーム呼ばない)。
7. API失敗時(Mac停止・Wi-Fi切断)の画面上の挙動を、アプリごとに決めておく。
8. アンケートを実施するアプリは、`survey.json` を置き、利用の終了時に `sdk.js` の終了処理を呼ぶ。

## 6. 設計ルール

1. ブラウザからは常に同一オリジンを呼ぶ。将来別マシンに処理を分ける場合も、振り分けはMac側で行う。ブラウザから別マシンを直接呼ぶとCORS設定が必要になる。
2. 状態を持つのは保存APIとアンケート回答(SQLite)だけにする。計算APIとメモリ上の変数には状態を持たせない。これにより、ワーカー数の変更や別マシンへの振り分けが可能になる。
3. アプリの `server.py` の読み込みに失敗しても、基盤全体は起動を続ける。失敗したアプリだけを無効にし、ログに残す。
4. 全アプリが1つのプロセスを共有する。1つのアプリの重い処理が他のアプリの応答を遅らせるため、監視画面で応答時間をアプリ単位で確認できるようにする。
5. 端末一覧、監視データ、アンケート回答を読み出す機能は、管理サーバにだけ置く。一般向けサーバには置かない。

## 7. 実装・運用上の注意

### FastAPI

- 重い処理のエンドポイントは `async def` ではなく `def` で書く。`def` はスレッドプールで実行されるが、`async def` 内の同期的な重処理はイベントループを止め、全端末が固まる。
- 一般向けサーバのルートの登録順は、API(`/api/*`)、`/core`、`/apps/<app>`、最後に `/` とする。`/` に `StaticFiles` を先にマウントすると、以降のパスがすべて静的配信に吸われる。
  ```python
  app.mount(f"/apps/{name}", StaticFiles(directory=f"apps/{name}/static", html=True), name=name)
  ```
- 起動例:
  - 一般向けサーバ: `uvicorn core.main:app --host 0.0.0.0 --port 3000`
  - 管理サーバ: `uvicorn core.admin:app --host 127.0.0.1 --port 3001`
- 純Pythonの重い計算はGILにより並列化されないため、プロセス並列(`ProcessPoolExecutor` または uvicorn の複数ワーカー)を検討する。
- アプリ更新後に、端末が古いJS/CSSをキャッシュし続けることがある。静的ファイルに `Cache-Control: no-cache` を付けるか、ファイル名にハッシュを含める。

### Mac・ネットワーク

- ルータのDHCP予約(または固定IP)でMacのIPを固定する。
- アクセス先URLは1つに固定する。端末内の保存データと端末IDはオリジン単位で分かれるため、`http://<Mac名>.local:3000` とIP指定を混在させると、別の端末として扱われ、データが消えたように見える。
  - Androidでは `.local` を解決できない場合があるため、IP指定を推奨する。
- macOSのファイアウォールで、使用ポート(仮想環境内のPython)の受信を許可する。
- スリープを防止する(省エネルギー設定または `caffeinate`)。`launchd` で自動起動し、可能なら有線LANで接続する。
- Pythonは `venv` か `uv` で仮想環境を作り、依存を固定する。`launchd` には仮想環境内のPythonをフルパスで指定する。

### 端末側の制約

- LAN内のhttpはセキュアコンテキストではないため、次のAPIが使えない。
  - Service Worker(PWA化)
  - `crypto.randomUUID()`、`crypto.subtle`
  - Clipboard API、カメラ・マイク
- 上記を使うにはHTTPSが必要。mkcertなどの自己署名証明書は端末ごとにインストールが要るため、後回しにする。
- iPhone/iPadのSafariは、サイトをしばらく使わないと端末内の保存データを削除することがある。端末IDも消えるため、サーバ側の保存データにもアクセスできなくなる(10章)。

## 8. 将来拡張

### RL推論

- 計算APIの実装の1つとして扱う。PyTorch(MPS)をFastAPIに載せ、モデルは起動時に1回だけロードする。
- ワーカーは1つにする。ワーカーごとにモデルがロードされ、メモリを消費するため。
- 小さなモデル(MLP程度)はCPUのほうが速いことがある。MPSとCPUを計測して決める。
- `def` エンドポイントは複数スレッドから同時に呼ばれる。MPSのマルチスレッド不安定が出たら、`threading.Lock` か専用スレッド+キューで推論を直列化する。
- 端末数が増えたら、短時間に届いた入力をまとめて推論するバッチ化を検討する。
- 環境ロジックをMac側(Python)に置くと、計算APIが状態を持つことになり、6章ルール2の例外となる。
- ONNX Runtimeへの変換は、必要になった時点で演算子の互換性とMPS対応を確認する。

### Raspberry Pi

- **当面は追加しない。** RL推論の高速化には効果が薄く、LAN往復のコストで逆に遅くなることがある。
- 役割を持たせるなら、ログ保存、`storage.db` のバックアップ先、予備機(縮退運転)、リバースプロキシが現実的。
- 処理の分担が必要になった場合は、Macを窓口にして、同じ計算APIを動かすPiへ振り分ける。計算APIがステートレスなので成立する。

### HTTPS

- PWAやセキュアコンテキスト必須のAPIが必要になった時点で検討する。証明書の配布方法(端末ごとのインストール)が主な課題になる。

## 9. 再検討のトリガー

| 条件 | 対応 |
|---|---|
| 端末間の同期・対戦、サーバからの通知が必要 | WebSocketを追加 |
| 端末をまたいで同じデータを使いたい | ユーザ単位の識別(認証)を追加 |
| 認証・管理操作・複雑なデータモデルが必要 | Djangoへの移行を検討 |
| PWAやセキュアコンテキスト必須APIが必要 | HTTPS化(証明書配布を含む) |
| 管理画面をMac以外の端末(スマホなど)から直接見たい | 管理サーバにパスワード認証とHTTPSを追加(証明書のインストールは管理者の端末だけで済む) |
| 宅外アクセスが必要 | 認証、VPNを追加 |
| RL推論を使う | 8章の方針に従う |
| Mac 1台で処理しきれない | 8章の方針でPiなどへ振り分け |

## 10. 未確定事項

- アプリ側から基盤に求められる要件: 計算の重さ、同時接続する端末数の上限、端末の種類
- アンケート回答を端末IDと紐付けるか、匿名にするか(当面は紐付ける。同じ端末の利用状況と照らし合わせられるため)
- 同じ端末に毎回アンケートを出すか、回答済みの版は出さないか
- 保存データの容量上限と保持期間、`metrics.db` の保持期間
- Safariのデータ削除などで端末IDが失われた場合の扱い。サーバ上のデータが誰のものか分からなくなる。案として、端末IDを画面に表示し、手入力で復元できるようにする方法がある
- RL推論を使うか。使う場合のモデルの種類・サイズと、環境ロジックの置き場所
