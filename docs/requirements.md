# システム基盤 要件整理(引き継ぎ用)

最終更新: 2026-10-05

## 1. 目的・スコープ

この文書は、同一LAN内の複数端末のブラウザからMac(M4)上の複数のアプリを使うための基盤を定める。アプリの内容は別途検討しているため、ここでは扱わない。

用語は次のとおり使い分ける。

| 用語 | 意味 |
|---|---|
| 端末 | 研究室が用意し、LANにつなぐクライアント機器。受付端末と展示用端末がある |
| 受付端末 | 参加者が最初に基本情報を入力する端末 |
| 展示用端末 | 参加者がアプリを使う端末。PCとタブレット |
| Mac | サーバ機 |
| アプリ | 基盤に載せる個々のWebアプリ |
| 参加者 | 来場し、受付端末で登録した人 |
| 公開サイト | 研究室兼広報用のWebサイト。この基盤とは別に、インターネット上で公開する |

### 基盤とアプリの境界

| 基盤が決める・提供するもの | アプリに任せるもの |
|---|---|
| サーバ、URL設計、アプリの配置規約 | 画面、操作、アプリ内のロジック |
| 端末ID、参加者の識別(受付・コード発行・ログイン) | |
| サーバ側保存、監視・ログ | 保存するデータの中身 |
| アンケートの表示・送信・集計の仕組み、基本情報と共通の体験評価の定義 | アプリ固有の設問の内容 |
| 計算APIを載せる仕組みと実装ルール | 計算の中身、どの処理をMacに置くかの判断 |
| クライアントSDK(`/core/sdk.js`) | SDKを使ったアプリ固有の処理 |

参加者は受付で発行したコードで識別する(4.8)。識別は記録と参加者を結び付けるためのもので、本人確認(認証)は行わない。

参加者のスマホはLANに参加しない。来場者は大学のWi-Fiに接続できないためである。スマホ向けのアプリは公開サイトで配信し、この基盤では扱わない。スマホでの記録は参加者と結び付けない。基盤がスマホに提供するのは、公開サイトに置く参加証ページ(4.8)だけとする。

宅外アクセス、本人確認による認証、リアルタイム通信(WebSocket)、PWA化、RL推論は当面の対象外とする。

## 2. 前提

| 項目 | 内容 |
|---|---|
| サーバ | Mac(M4)1台 |
| ネットワーク | 同一LANのみ。宅外からはアクセスしない。LANからインターネットには接続できる |
| 端末 | 受付端末と、展示用端末(PC・タブレット)が複数台。いずれも研究室が用意する |
| 参加者のスマホ | LANには接続しない。モバイル回線で公開サイトの参加証ページを開くだけとする |
| アクセス制御 | 一般向けの画面・APIには、LAN内の機器なら誰でも接続できる。管理画面はMac本体からのみ開ける |
| アプリ | 複数。参加者は展示用端末でログインしたあと、ランチャー画面から選んで起動する |
| 言語 | サーバ側はPython(FastAPI / uvicorn) |
| データ | 端末内保存と、Macでの参加者単位の保存を併用する |
| 処理の分担 | 軽い処理は端末で、重い処理だけMacの計算APIで行う。どこで分けるかはアプリごとに判断する |

## 3. 全体構成

Mac上では、一般向けサーバと管理サーバの2つのプロセスを動かす。

```
[受付端末・展示用端末のブラウザ]       [一般向けサーバ 0.0.0.0:3000]
  受付画面 / ランチャー / 各アプリ ──HTTP──>   /               ランチャー(ログイン前は待機画面)
  sdk.js(端末ID・ログイン・API呼び出し)       /reception/     受付画面
  端末内保存(localStorage等)                  /apps/<app>/    各アプリの静的ファイル
                                              /api/<app>/*    各アプリの計算API(状態なし)
                                              /api/core/*     基盤API(受付・ログイン・保存・アンケート回答・端末・ヘルスチェック)
                                                  │ 書き込み
                                              data/  storage.db / metrics.db / logs
                                                  │ 読み取り専用
[Mac本体のブラウザ]           ──HTTP──>       [管理サーバ 127.0.0.1:3001]
                                              監視画面・参加者一覧・アンケート集計・CSV出力

[参加者のスマホ(モバイル回線)] ──HTTPS──>   [公開サイト]
                                              参加証ページ(静的HTML)、スマホ向けアプリ
                                              ※ Macとは通信しない
```

### URL設計

#### 一般向けサーバ(`http://<MacのIP>:3000`)

| パス | 内容 |
|---|---|
| `/` | ランチャー。ログイン前は待機画面(コード入力)を表示し、ログイン後は `apps/` 配下のアプリを一覧表示する |
| `/reception/` | 受付画面(4.8) |
| `/apps/<app>/` | アプリの静的ファイル |
| `/api/<app>/*` | アプリの計算API |
| `/api/core/reception` | 基本情報の定義の取得(GET)、基本情報の登録とコードの発行(POST) |
| `/api/core/login` | コードによるログイン(POST)、ログアウト(DELETE) |
| `/api/core/storage/<app>/<key>` | 保存API(GET / PUT / DELETE) |
| `/api/core/surveys/<app>` | アンケート定義の取得(GET。共通の体験評価を含む)、回答の送信(POST) |
| `/api/core/devices` | 端末情報の登録・更新 |
| `/api/core/health` | ヘルスチェック |
| `/core/*` | 基盤の静的ファイル(`sdk.js` など) |

すべてのパスを同一オリジン(同じホスト・ポート)から配信するので、CORSの設定は要らない。

#### 管理サーバ(`http://localhost:3001`)

| パス | 内容 |
|---|---|
| `/` | 監視画面(4.4) |
| `/participants` | 参加者一覧(4.8) |
| `/surveys` | アンケート集計とCSVダウンロード(4.6) |

管理サーバの詳細は4.7に記載する。

### ディレクトリ構成

```
akabane2026/
  core/              基盤のPythonコード(起動、アプリ読み込み、受付・ログイン、保存、監視)
    main.py          一般向けサーバ
    admin.py         管理サーバ
    static/          ランチャー、受付画面、sdk.js
    admin_static/    監視画面、参加者一覧、アンケート集計画面
    surveys/
      profile.json   基本情報の定義(受付で聞く)
      common.json    共通の体験評価の定義(各アプリの終了時に聞く)
  apps/
    <app>/
      app.json       表示名・説明など(ランチャー用)
      survey.json    任意。アプリ固有の設問を聞く場合のみ
      static/        index.html ほか
      server.py      任意。計算APIを持つ場合のみ
  site/
    pass/            参加証ページ。公開サイトに配置する(4.8)
  data/              storage.db(参加者・保存データ・アンケート回答)、metrics.db、ログ
                     (バックアップ対象は storage.db)
```

基盤のパッケージ名には `platform` を使わない。Python標準ライブラリの `platform` モジュールと名前が衝突するためである。

## 4. 基盤の機能

### 4.1 端末ID

- 端末が初めてアクセスしたとき、`sdk.js` が `crypto.getRandomValues()` で128bitの乱数を生成してlocalStorageに保存する。LAN内のhttpでは `crypto.randomUUID()` が使えないため、この方法をとる。
- 同じく初回アクセス時に、`sdk.js` はUser-Agentと任意の表示名を `/api/core/devices` へ送る。管理者は端末の設置時に表示名(例: 「展示PC-1」)を付け、監視画面でこの情報を見て端末を見分ける。
- `sdk.js` はすべてのAPI呼び出しに、端末IDを `X-Device-Id` ヘッダで付ける。
- 端末IDは端末を見分けるためのもので、参加者の識別には使わない(4.8)。LAN内の誰でも他の端末のIDを名乗れる。

### 4.2 計算API

- 基盤は、アプリの `server.py` が公開する `APIRouter` を `/api/<app>` 配下に登録する。
- 計算APIは状態を持たない。状態が必要な場合は、端末が保持してリクエストに含めて送る。
- 入出力はJSONとし、Pydanticモデルでスキーマを定義する。
- 重い処理は `def` で書く(7章)。

### 4.3 保存API

- 基盤の中で状態を持つのは、参加者とログインの情報(4.8)、保存API、アンケート回答(4.6)だけとする。
- 保存APIは、(アプリ名, 参加者ID, キー) を主キーとしてJSON値をSQLite(`data/storage.db`)に保存する。同じ参加者なら、別の展示用端末からでも同じデータを読める。
- 保存APIはログイン中だけ使える。基盤は `X-Login-Id` ヘッダ(4.8)から参加者IDを求める。ログインしていない呼び出しはエラーにする。
- 値のサイズには上限を設ける(仮に1件1MB)。
- SQLiteはWALモードで使う。接続はリクエストごとに開き、スレッド間で共有しない。
- 書き込み中のファイルを単純にコピーすると、コピー先が破損することがある。そのためバックアップには、SQLiteのオンラインバックアップ(`sqlite3 storage.db ".backup ..."`)を `launchd` で定期実行する。

### 4.4 監視・ログ

- 基盤はミドルウェアで全リクエストの時刻、端末ID、アプリ名、パス、ステータス、処理時間を記録する。
  - 記録先はSQLite(`data/metrics.db`)とし、保持期間を過ぎた記録は削除する。複数ワーカーでも集計できるように、記録をメモリ上には持たない。
  - アプリケーションログはJSON形式でファイルに出力し、ローテーションする。
- 管理サーバの監視画面では、次の情報を確認できる。画面は閲覧専用とし、データの削除などの操作は置かない。
  - 接続中の端末(直近5分以内にリクエストかハートビートがあった端末)と、各展示用端末のログイン状態
  - アプリ・APIごとの呼び出し数と応答時間
  - エラーの一覧
- `sdk.js` は、画面が表示されている間、1分に1回ハートビートを送る。
- `/api/core/health` は、監視や `launchd` 運用での死活確認に使う。

### 4.5 クライアントSDK(`/core/sdk.js`)

アプリごとに同じ処理を作り直さずに済むよう、SDKは次の機能を提供する。

- 端末IDの生成・取得
- ログインとログアウト(待機画面、コード入力、確認画面、無操作時の自動ログアウト。4.8)
- API呼び出し(`X-Device-Id` と `X-Login-Id` の付与、タイムアウト、失敗時のエラー形式の統一)
- 保存APIの読み書き
- ハートビート
- セッションの開始・終了と、終了時のアンケート表示(4.6)
- 受付画面とアンケート画面で共通に使う、設問の表示部品

### 4.6 アンケート

参加者に聞く設問は、次の3種類に分ける。

| 種類 | 定義ファイル | 聞く回数 | 聞く場所 |
|---|---|---|---|
| 基本情報 | `core/surveys/profile.json` | 1人1回 | 受付端末(4.8) |
| 共通の体験評価 | `core/surveys/common.json` | 1回の利用ごと | 各アプリの終了時。全アプリで同じ設問 |
| アプリ固有の設問 | `apps/<app>/survey.json` | 1回の利用ごと | 各アプリの終了時。共通の体験評価のあとに出す |

基本情報には、年代やゲーム経験など、使うアプリによらない参加者の属性を入れる。楽しさや難しさのように、使った直後でないと答えられない設問は共通の体験評価に入れる。設問をそろえておくと、アプリどうしを比べられる。

基本情報と共通の体験評価の設問は、研究の目的に合わせて後から決める。当面は仮の設問(ニックネームと数問)で仕組みを作り、設問が決まったら定義ファイルを差し替える。

#### 実施の流れ

1. アプリの起動時に、`sdk.js` がセッションIDを発行する。1回の利用を1セッションとする。
2. アプリは終了時に `sdk.js` の終了処理(例: `core.finish()`)を呼ぶ。ブラウザのタブが閉じられたことは確実には検知できないため、アプリが終了を明示的に知らせる。
3. `sdk.js` は、共通の体験評価とアプリ固有の設問を続けて表示する。`survey.json` がないアプリでは、共通の体験評価だけを表示する。
4. 参加者が回答すると、`sdk.js` は回答を送信してランチャーに戻る。「スキップ」を選んだ場合は、送信せずにランチャーに戻る。

#### アンケート定義

- `profile.json`、`common.json`、`survey.json` は同じ形式とする。表示も `sdk.js` の同じ部品が担うので、アプリはアプリ固有の設問を書くだけでよい。
- 設問の形式は、単一選択、複数選択、段階評価(例: 1〜5)、自由記述の4種類とする。
- 設問ごとに必須・任意を指定できる。終了時のアンケートは、参加者が全体をスキップできる。
- 定義には `version` を持たせる。設問を変えたら `version` を上げる。基盤は回答に `version` を記録し、どの版への回答かを区別する。共通の体験評価とアプリ固有の設問の `version` は別々に記録する。

#### 回答の保存

- 回答は `storage.db` の専用テーブルに保存し、保存データと同じくバックアップの対象にする。
- 1件の回答には、アプリ名、共通の体験評価とアプリ固有の設問それぞれの `version`、セッションID、参加者ID、端末ID、回答日時、セッションの長さ、各設問の回答を記録する。
- 基本情報は参加者のデータとして保存する(4.8)。
- 送信に失敗した回答は端末内に保存し、`sdk.js` が次回アクセス時に再送する。二重登録はセッションIDで防ぐ。
- 自由記述には文字数の上限を設ける(仮に1問1000文字)。

#### 集計

- 管理サーバの集計画面では、アプリ・版ごとの回答数、選択式設問の集計、自由記述の一覧を見られる。
- 回答はアプリ・版ごとにCSVでダウンロードできる。CSVには参加者IDで基本情報の列を結合して出力する。ただし、確認用のニックネームはCSVに含めない。詳しい分析は、CSVを使って基盤の外で行う。
- 一般向けサーバには回答の送信APIだけを置き、回答を読み出すAPIは置かない。

### 4.7 管理サーバ

監視画面、参加者一覧、アンケート集計は、一般向けサーバとは別のプロセス(管理サーバ)で提供する。管理サーバにはMac本体からしか接続できないようにする。

- 管理サーバは `127.0.0.1:3001` で待ち受ける。LAN上の他の機器からは接続する経路がないため、パスワードなどの認証は置かない。
  - **待ち受けアドレスを `0.0.0.0` に変えてはならない。** 変えると、LAN内の誰でも管理画面を開ける状態になる。
- 管理者はMac本体のブラウザで `http://localhost:3001` を開いて使う。
- 別のPCから見る場合は、Macの「リモートログイン」(SSH)を有効にしたうえで、SSHのポート転送を使う。
  ```
  ssh -L 3001:localhost:3001 <ユーザ名>@<MacのIP>
  ```
  接続後、そのPCのブラウザで `http://localhost:3001` を開く。
- 管理サーバは `storage.db` と `metrics.db` を読み取り専用モード(`file:...?mode=ro`)で開く。書き込みは一般向けサーバだけが行う。受付画面を管理サーバに置かないのはこのためである。
- 管理サーバは一般向けサーバとは別の `launchd` ジョブとして常駐させる。管理サーバが止まっても、一般向けサーバは動き続ける。

### 4.8 参加者の識別

参加者が受付端末で基本情報を入力すると、基盤はコードを発行する。参加者はそのコードで展示用端末にログインする。識別の目的は、展示用端末での記録とアンケート回答を、受付で入力した基本情報と結び付けることにある。

なりすましの防止は目的にしない。教室内での利用であり、なりすましの影響は研究データの一部が汚れる程度にとどまるためである。対策が必要なのは、コードの打ち間違いや、前の参加者のログインが残ることによる取り違えのほうである。

紙(カードや印刷物)は使わない。コードは、参加者が自分のスマホの参加証ページで持ち歩く。

#### 受付

1. 参加者は受付端末の `/reception/` で、研究利用への同意を確認し、基本情報(`profile.json`)を入力する。
2. 一般向けサーバは参加者IDとコードを発行し、基本情報とともに `storage.db` に保存する。
3. 受付画面は、コードを大きな文字で表示する。あわせて、参加証ページのURL(`https://<公開サイト>/pass/#<コード>`)をQRで表示する。
4. 参加者はスマホの標準カメラでQRを読み、参加証ページを開く。スマホを使わない参加者は、コードを覚える。

#### コード

- 5文字程度の英数字とする。紛らわしい文字(`0/O`、`1/I/l` など)は使わない。
- 乱数で発行し、連番にはしない。有効な参加者のあいだで重複しないようにする。
- 有効期限は当日限りとする(仮)。期限を過ぎたコードではログインできない。
- コードは参加者IDとは別の値とする。CSVや分析には参加者IDを使い、コードは出力しない。

#### 参加証ページ

- 公開サイトに置く1枚の静的HTMLとする。バックエンドは持たない。ソースは `site/pass/` で管理する。
- コードはURLの `#` 以降に入れる。`#` 以降はサーバに送られないので、ホスティング先のアクセスログにも残らない。
- ページは、コードを大きな文字とQRで表示する。QRはページ内のJSで生成する。
- ページはコードを端末内に保存し、次に開いたときも表示する。
- ページにはコード以外の情報(基本情報など)を載せない。
- 研究室サイトの公開が間に合わない場合は、GitHub Pagesなど別のホスティングに置く。

#### 展示用端末でのログイン

1. ログインしていない展示用端末は、ランチャー(`/`)に待機画面を表示する。
2. 参加者は参加証ページに表示されたコードを入力する。
3. `sdk.js` はコードを `/api/core/login` へ送る。一般向けサーバは参加者と端末を結び付けてログインIDを発行し、確認用のニックネームとともに返す。
4. 待機画面は「〇〇さんですか?」と確認する。参加者が「いいえ」を選んだら、`sdk.js` はログアウトして待機画面に戻る。
5. ログイン中、`sdk.js` はAPI呼び出しにログインIDを `X-Login-Id` ヘッダで付ける。ログインIDは端末内(sessionStorage)に保存する。

- 1人の参加者がログインできる展示用端末は1台とする。別の展示用端末でログインすると、前の端末のログインを解除する。
- コードを照合するAPIには、端末ごとの試行回数の制限を設ける。

#### ログアウト

次のいずれかでログアウトし、待機画面に戻る。

- 終了時のアンケートを送信またはスキップしたとき
- 参加者がランチャーの「終わる」ボタンを押したとき
- 一定時間(仮に3分)操作がなかったとき

#### 読み取り方法の拡張

当面はコードの手入力だけで運用する。入力が混雑の原因になったら、次のどちらかを追加する。どちらの場合も手入力は予備の手段として残す。

| 方法 | 内容 |
|---|---|
| 2次元コードスキャナ | 参加証ページのQRをスキャナで読む。スキャナはキーボードとして入力するので、待機画面の変更はほぼ要らない。PCにはUSB、タブレットにはBluetoothの機種を使う。スマホ画面を読める機種を選ぶ |
| 展示用端末のカメラ | 展示用端末をHTTPSで接続し、ブラウザからカメラでQRを読む(8章) |

#### 参加者のデータ

- 参加者テーブルには、参加者ID、コード、コードの有効期限、受付日時、基本情報とその `version` を保存する。
- ログインテーブルには、ログインID、参加者ID、端末ID、ログイン日時、最終操作日時を保存する。
- 参加者一覧は管理サーバでだけ見られる(6章ルール5)。一般向けサーバのログインAPIが返すのは、入力されたコードに対応する参加者のニックネームだけとする。

## 5. アプリ組み込み規約

1. アプリ名は `[a-z0-9-]+` とする。`core` は予約語とする。
2. `apps/<app>/` にディレクトリを置くと、基盤の再起動時にランチャーと配信に反映される。
3. `server.py` は任意。置く場合は `router = APIRouter()` を公開する。
4. localStorageとIndexedDBは同一オリジンの全アプリで共有される。キーとDB名は `<app>:` で始める。展示用端末は複数の参加者が使い回すので、参加者ごとのデータは端末内ではなく保存APIに置く。
5. 計算の呼び出し口は `compute()` のような1つの関数に集約する。最初は端末内で実行し、重ければ中身をAPI呼び出しに差し替える。差し替えても呼び出し側を変えずに済むよう、最初から `async`(Promiseを返す)にしておく。
6. APIは必要なタイミングだけ呼ぶ。毎フレーム呼んではならない。
7. API呼び出しが失敗したとき(Mac停止・Wi-Fi切断)の画面上の挙動を、アプリごとに決めておく。
8. すべてのアプリは、利用の終了時に `sdk.js` の終了処理を呼ぶ。終了処理がアンケートの表示とログアウトを行う。アプリ固有の設問を聞くアプリは `survey.json` を置く。
9. 公開サイトでも配信する可能性があるアプリは、`sdk.js` がなくても動くように作る。`sdk.js` の呼び出しはアプリ内の1ファイルにまとめ、`sdk.js` がなければ何もしないようにする(例: `apps/dijkstra-delivery` の `core-adapter.js`)。

## 6. 設計ルール

1. ブラウザからは常に同一オリジンを呼ぶ。ブラウザから別マシンを直接呼ぶとCORSの設定が必要になるため、将来処理を別マシンに分ける場合も振り分けはMac側で行う。
2. 状態を持つのは、参加者とログインの情報、保存API、アンケート回答(SQLite)だけにする。計算APIとメモリ上の変数には状態を持たせない。このルールを守れば、ワーカー数を変えたり処理を別マシンへ振り分けたりできる。
3. アプリの `server.py` の読み込みに失敗しても、基盤全体は起動を続ける。基盤は失敗したアプリだけを無効にし、ログに残す。
4. 全アプリが1つのプロセスを共有するので、あるアプリの重い処理が他のアプリの応答を遅らせる。監視画面では、応答時間をアプリ単位で確認できるようにする。
5. 端末一覧、参加者一覧、監視データ、アンケート回答を読み出す機能は、管理サーバにだけ置く。一般向けサーバには置かない。

## 7. 実装・運用上の注意

### FastAPI

- 重い処理のエンドポイントは `async def` ではなく `def` で書く。FastAPIは `def` のエンドポイントをスレッドプールで実行する。一方、`async def` の中で同期的な重い処理を行うとイベントループが止まり、全端末への応答が止まる。
- 一般向けサーバのルートは、API(`/api/*`)、`/core`、`/reception`、`/apps/<app>`、`/` の順に登録する。`/` に `StaticFiles` を先にマウントすると、以降のパスへのリクエストもすべて静的ファイル配信が受け取ってしまう。
  ```python
  app.mount(f"/apps/{name}", StaticFiles(directory=f"apps/{name}/static", html=True), name=name)
  ```
- 各サーバは次のコマンドで起動する。
  - 一般向けサーバ: `uvicorn core.main:app --host 0.0.0.0 --port 3000`
  - 管理サーバ: `uvicorn core.admin:app --host 127.0.0.1 --port 3001`
- 純Pythonの重い計算はGILのため並列に実行されない。その場合はプロセス並列(`ProcessPoolExecutor` またはuvicornの複数ワーカー)を検討する。
- アプリを更新しても、端末が古いJS/CSSをキャッシュから使い続けることがある。静的ファイルに `Cache-Control: no-cache` を付けるか、ファイル名にハッシュを含める。

### Mac・ネットワーク

- ルータのDHCP予約(または固定IP)でMacのIPを固定する。
- アクセス先のURLは1つに固定する。端末内の保存データと端末IDはオリジン単位で分かれる。`http://<Mac名>.local:3000` とIP指定を混在させると、同じ端末が別の端末として扱われ、データが消えたように見える。
  - Androidは `.local` を解決できない場合があるため、IP指定を推奨する。
- macOSのファイアウォールで、使用ポート(仮想環境内のPython)の受信を許可する。
- 省エネルギー設定または `caffeinate` でスリープを防止する。サーバは `launchd` で自動起動し、可能ならMacを有線LANで接続する。
- Pythonは `venv` か `uv` で仮想環境を作り、依存パッケージのバージョンを固定する。`launchd` には仮想環境内のPythonをフルパスで指定する。

### 端末側の制約

- LAN内のhttpはセキュアコンテキストではないため、次のAPIが使えない。
  - Service Worker(PWA化)
  - `crypto.randomUUID()`、`crypto.subtle`
  - Clipboard API、カメラ・マイク
- 上記のAPIを使うにはHTTPSが必要になる(8章)。
- iPhone/iPadのSafariは、しばらく使われていないサイトの端末内保存データを削除することがある。展示用のタブレットで端末IDが消えると、監視画面では別の端末として扱われる。参加者のデータは参加者IDに結び付けてMacに保存しているので、失われない。

## 8. 将来拡張

### RL推論

- RL推論は計算APIの実装の1つとして扱う。PyTorch(MPS)をFastAPIに載せ、モデルは起動時に1回だけロードする。
- ワーカーは1つにする。ワーカーごとにモデルがロードされ、その分メモリを消費するためである。
- MLP程度の小さなモデルは、CPUで動かしたほうが速いことがある。MPSとCPUの両方で計測して決める。
- `def` エンドポイントは複数スレッドから同時に呼ばれる。MPSがマルチスレッドで不安定になった場合は、`threading.Lock` か専用スレッドとキューを使って推論を直列化する。
- 端末数が増えたら、短時間に届いた入力をまとめて推論するバッチ化を検討する。
- 環境ロジックをMac側(Python)に置くと計算APIが状態を持つことになり、6章ルール2の例外となる。
- ONNX Runtimeへの変換は、必要になった時点で演算子の互換性とMPS対応を確認してから行う。

### Raspberry Pi

- **当面は追加しない。** PiはRL推論の高速化にほとんど役立たず、LANの往復時間のぶん逆に遅くなることがある。
- 役割を持たせるなら、ログ保存、`storage.db` のバックアップ先、予備機(縮退運転)、リバースプロキシが現実的である。
- 処理の分担が必要になった場合は、Macを窓口にして、同じ計算APIを動かすPiへリクエストを振り分ける。計算APIがステートレスなので、この構成をとれる。

### HTTPS

- PWAやセキュアコンテキスト必須のAPIが必要になった時点で検討する。
- 端末はすべて研究室が用意し、参加者の端末はLANに参加しない。そのため、証明書をインストールする先は受付端末と展示用端末の数台で済む。mkcertでMacのIPに対する証明書を作り、各端末にルート証明書を入れる。
- 展示用端末のカメラで参加証のQRを読む場合(4.8)は、この方法でHTTPS化する。
- HTTPSに移ると端末のオリジンが変わり、端末IDと端末内の保存データは引き継がれない。

## 9. 再検討のトリガー

## 10. 未確定事項

- アプリ側から基盤に求められる要件。計算の重さ、展示用端末の台数、1回の参加者数がまだ分かっていない。
- 基本情報と共通の体験評価の設問内容。研究の目的に合わせて決める。それまでは仮の設問で進める。
- 研究利用への同意の取り方。参加者に未成年が含まれる場合は、大学の倫理審査で保護者同意の要否を確認する。
- 退場時のアンケート(全体の感想、事後の理解度)を設けるか。設けるなら、受付で聞く事前知識と同じ尺度にして前後を比べられるようにする。
- 共通の体験評価を全アプリで必ず出すか、アプリごとに出すかどうかを選べるようにするか。
- 同じ参加者が同じアプリを再び使ったとき、終了時のアンケートを毎回出すか、初回だけにするか。
- 受付APIのアクセス制御。一般向けサーバに置くので、LAN内の誰でも呼べる。教室内なので許容するか、受付端末だけが知る合言葉を付けるかを決める。
- スマホを使わず、コードも覚えられない参加者への対応。案として、待機画面に直近の受付者をニックネームとアイコンで並べ、選ばせる方法がある。ただしこの方法は、一般向けサーバから参加者の情報を読み出すことになり、6章ルール5の例外となる。
- コードの有効期限と、参加者が後日再び来場したときの扱い。
- 無操作で自動ログアウトするまでの時間。
- 公開サイトのホスティング方法。参加証ページの置き場所もこれに従う。
- 保存データの容量上限と保持期間、`metrics.db` の保持期間。
- RL推論を使うか。使う場合は、モデルの種類・サイズと環境ロジックの置き場所も決める。
