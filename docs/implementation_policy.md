# 実装方針

- 作成日: 2026-10-06
- 対象: リポジトリ全体(研究室サイト `lab-site/` と、基盤に載せるアプリ `apps/*`)
- 関連: 基盤の要件 `docs/requirements.md`、ゲームの設計 `docs/dijkstra_game_design.md`、トップ表現の検討 `docs/lab_site_top_concepts.md`

---

## 1. 配信先ごとの技術選定

このリポジトリには配信先が2つあり、配信先に合わせて書き方を変える。ブラウザが受け取るのはどちらもJavaScriptで、違うのは書く言語とビルドの有無である。

| | 研究室サイト `lab-site/` | 基盤のアプリ `apps/*` |
|---|---|---|
| 配信先 | GitHub Pages(インターネットに公開) | 基盤(Mac / Raspberry Pi、同一LANのみ) |
| 書く言語 | TypeScript(strict) | JavaScript(ESモジュール)+ JSDocで型 |
| ビルド | あり(Vite)。GitHub Actionsがビルドして公開する | なし。`static/` をそのまま配信する |
| 型チェック | `tsc` | `tsc --noEmit`(`checkJs`)※未導入 |
| テスト | Vitest(処理)+ Playwright(見た目と挙動) | `node --test` |
| 外部依存(実行時) | Google Fontsのみ | なし |

- **アプリをビルドなしにする理由**: 基盤は `apps/{name}/static` をそのまま配信する(`docs/requirements.md` 4章)。ビルドを入れると、「`apps/` に置いて再起動するだけで動く」という基盤の利点がなくなる。生成物をコミットすると、元のコードとずれるおそれもある。新しいアプリも、基盤の規約が変わらない限り同じ方針にする
- **サイトをビルドありにする理由**: GitHub PagesにはActionsでビルドしてから公開できるので、ビルドの手間は自動化で省ける。そのうえで、型、モジュールの分割、圧縮が使え、公開版からだけ検証用のUIを外せる
- 型の書き方は違っても、型チェックはどちらもTypeScriptのコンパイラで行う。JSDocで型を付けておけば、将来アプリをTypeScriptに移すときも機械的に書き換えられる

## 2. 研究室サイトの公開

- `.github/workflows/lab-site.yml` が、pushとPRのたびにチェックとテスト(5章)を実行する
- `main` へのpushでテストが通れば、`lab-site/dist/` をGitHub Pagesに公開する。公開されるのはビルド結果だけで、`docs/` などリポジトリのほかの部分は出ない
- 出力は相対パス(Viteの `base: "./"`)。`https://custard-1855.github.io/akabane2026/` のようなサブパスでも、将来の独自ドメインでも、設定を変えずに動く
- 初回だけ、リポジトリのSettings → PagesのSourceを「GitHub Actions」にする
- ブランチから直接公開する方式は使わない(公開元に選べる `/docs` は設計書で使っているため)

## 3. コードの構成

### 3.1 層と依存の向き

役割ごとにファイルを分け、**上の層は下の層を使い、下の層は上の層を知らない**。抽象クラスやインターフェースは足さず、「そのファイルが何を知っているか」で分ける。

```
main.ts         DOM・入力・時間の接続          ← 画面のことを全部知っている
  ↓
render.ts       canvas への描画                ← canvas は知っている。DOM の部品は知らない
scene.ts        状態と時間の進行               ← 時間は知っている。描き方と DOM は知らない
  ↓
algorithms.ts   グラフ → 出来事の列            ← 純粋な計算。画面も時間も知らない
  ↓
graphs.ts       形のデータ                     ← 点と辺の配列を返すだけ
```

- 下の層(`algorithms.ts`・`graphs.ts`)はDOMなしで動くので、Node上で直接テストできる
- `scene.ts` はDOMに触らない。形や処理の名前が変わったことは、フック(`onShapeLoad` など)で `main.ts` に知らせる
- 処理は実際に計算し、起きた順に出来事の列を返す。再生(時間)と描画は別の層が受け持つ
- アプリ側(`apps/dijkstra-delivery/`)も同じ考え方で、`logic.js` はDOMに依存せず、`view.js` は状態を持たない(設計書3.4〜3.5)

### 3.2 検証用のUI

- 検証用の操作(ヒーローの図形切り替えなど)は、開発サーバー(`import.meta.env.DEV`)か、URLに `?dev` を付けたときだけ出す
- 公開ページの見た目には出さないが、公開先でも `?dev` で確かめられる

### 3.3 試作の扱い

- 検討用の試作は `lab-site/prototypes/` に置いて凍結する。ビルド・公開・整形・作り直しの対象にしない
- 採用した案は、試作を直さずに本体(`lab-site/src/`)へ移して作り直す。試作は検討の記録として残す

## 4. コードの書き方

- 整形はPrettier(行の長さ100、文字列はダブルクォート)、静的チェックはESLint(typescript-eslint)、型はTypeScriptのstrict
- コメント・テスト名・コミットメッセージは日本語。コメントには「何をするか」より「なぜそうするか」を書く
- 調整用の値(速さ、間隔、数など)は `config.ts` の `CFG` に集める
- 乱数を使う処理は `Math.random` を直接使う。テストでは `Math.random` を差し替えて種を固定する

## 5. テストと検証

### 5.1 テストの種類(研究室サイト)

| 種類 | 道具 | 確かめること |
|---|---|---|
| 処理のテスト | Vitest(`npm test`) | 形の頂点数・辺数・次数、幅優先探索、彩色の結果が正しい塗り分けか、2色の判定で示す奇数の輪が本物か |
| 見た目のテスト | Playwright(`npm run test:e2e`) | 乱数と時間を固定し、canvasの絵をベースライン画像と画素単位で比べる |
| 挙動のテスト | Playwright | 形の切り替え、クリック、テーマ、検証用ボタン、動きを減らす設定、レイアウト |

- 見た目のテストは、Webフォントを読み込まず、canvasの中身だけを半分の大きさで比べる(文字の描画や環境差に左右されないようにするため)
- 見た目を意図して変えたときは `npm run test:e2e:update` でベースラインを更新し、更新した画像も同じコミットに入れる
- テストは公開するものと同じビルド結果(`dist/`)に対して動かす

### 5.2 作り直しの進め方

1. **先に、今の実装に対するテストを作る**。実装には手を入れない
2. テストが変化を検出できるか確かめる(実装をわざと少し変えて失敗することを見て、元に戻す)
3. 作り直す。挙動を変えない変更(整形、移動、分割、名前の変更)と、挙動を変える変更は別のコミットにする
4. 挙動を変えない変更では、テストを書き換えずに通ることを確認する。テストを直す必要が出たら、実装の仕様を確かめ直し、分かったことを記録する

- テストで見つかった既存の不具合は、すぐ直さずに `test.fail` で記録する(直したら外す)。直す作業は別のコミットにする
- `npm run check`(整形・ESLint・型チェック・処理のテスト)と見た目・挙動のテストが通ってからpushする

## 6. 未着手・既知の課題

| 項目 | 内容 |
|---|---|
| 名前と構造の改善 | 出来事のフィールド名(`e`・`c`・`w` など)を意味の分かる名前にする。`draw()` を分割する。描画中にホバーの状態を書き換えている所を `scene` に移す。ヒーローで使っていない貪欲彩色と結果の文を整理する |
| 既知の不具合 | 動きを減らす設定で検証用のボタンから形を選ぶと、フェードインが進まず何も描かれない(`test.fail` で記録済み) |
| 結果の文のずれ | 辺の塗り分けの結果の文は「試した色数」を出すので、実際に使った色数より多く出ることがある(ヒーローは結果の文を出さないので影響なし) |
| アプリ側の仕組み | `apps/dijkstra-delivery/` にPrettier・ESLint・型チェック(`checkJs`)はまだ入れていない |
| ベースライン画像の容量 | 合計3.8MB。更新するたびにリポジトリの履歴が増える |
