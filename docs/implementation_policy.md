## 1. 技術選定

| | ゲームのアプリ `apps/*` |
|---|---|
| 配信先 | Django の静的ファイル。置き場所と URL は組み込むときに決める(設計書 3.8)。開発中は静的サーバで動かす。main の `static/` は GitHub Pages(https://custard-1855.github.io/akabane2026/)にも公開する(`.github/workflows/games.yml`) |
| 書く言語 | JavaScript(ESモジュール)+ JSDocで型 |
| ビルド | なし。`static/` をそのまま配信する |
| 型チェック | `tsc --noEmit`(`checkJs`)※未導入 |
| テスト | `node --test` |
| 外部依存(実行時) | なし |

- **ビルドなしにする理由**: `static/` を置くだけで、静的サーバでも Django の静的ファイルとしても同じものが動く。ビルドを入れると、Django 側に生成物を置く手順が増える。生成物をコミットすると、元のコードとずれるおそれもある。新しいアプリも同じ方針にする
- 見た目は特設サイトに揃える。特設サイトの `tokens.css` とフォントを `static/` にコピーし、先頭にコピー元のコミットを書く。実行時に特設サイトから読み込まないのは、会場でネットにつながらないと崩れるためである(設計書 3.7)
- 型チェックはTypeScriptのコンパイラで行う。JSDocで型を付けておけば、将来TypeScriptに移すときも機械的に書き換えられる

## 2. コードの構成

役割ごとにファイルを分け、**上の層は下の層を使い、下の層は上の層を知らない**。抽象クラスやインターフェースは足さず、「そのファイルが何を知っているか」で分ける。

- 計算(ゲームの規則、探索など)はDOMに依存しないファイルに置き、Node上で直接テストする
- 画面のファイルは状態を持たず、計算の結果を描くだけにする
- 例: `apps/dijkstra-delivery/` では、`logic.js` はDOMに依存せず、`view.js` は状態を持たない(設計書3.4〜3.5)。研究室サイトのヒーロー(kawahara-lab-site の `src/hero/`)も同じ考え方で分けている
- 検証用の操作は、URLに `?dev` を付けたときだけ出す。公開する画面の見た目には出さない

## 3. コードの書き方

- コメント・テスト名・コミットメッセージは日本語。コメントには「何をするか」より「なぜそうするか」を書く
- 調整用の値(速さ、間隔、数など)は1か所(`config.js` など)に集める
- 乱数を使う処理は `Math.random` を直接使う。テストでは `Math.random` を差し替えて種を固定する

## 4. 作り直しの進め方

1. **先に、今の実装に対するテストを作る**。実装には手を入れない
2. テストが変化を検出できるか確かめる(実装をわざと少し変えて失敗することを見て、元に戻す)
3. 作り直す。挙動を変えない変更(整形、移動、分割、名前の変更)と、挙動を変える変更は別のコミットにする
4. 挙動を変えない変更では、テストを書き換えずに通ることを確認する。テストを直す必要が出たら、実装の仕様を確かめ直し、分かったことを記録する

- テストで見つかった既存の不具合は、すぐ直さずに記録する(`node --test` なら `todo` を付ける)。直す作業は別のコミットにする

## 6. 特設サイト `site/`

スカラベ・ネットワーク研究会の特設サイトを、このリポジトリの `site/` に置く。赤羽台祭の前は告知、祭の後は同じURLのままアーカイブにする。更新するのはこのリポジトリの作成者1人である。告知の始め方は 6.4。作業の一覧は `docs/site_todo.md`。

### 6.1 範囲

- 2ページ: トップと展示紹介
  - トップ: 企画の紹介、スカラベの解説、日時と場所、展示紹介と研究室サイトへのリンク
  - 展示紹介: 1ページにまとめ、展示物ごとに節を立てる。各節で、何を体験できるかと、グラフから通信ネットワークへのつながりを書く。長くなったらページを分ける
- 展示紹介に載せるのは、出すと決まった展示物だけにする。今はグラフであそぼうと、ほかのメンバーの3つ(名前は仮)
  - グラフであそぼうは1つの節にまとめ、ゲームを選ぶ画面に出す4本(配達員ダイクストラと試作の3本)ごとに小見出しを立てる。試作には「試作」の札を付ける
  - ゲームの節には、最終版の画面写真(管制室を進めている途中)を1枚載せる。遊べるリンクは置かない
- 日時と場所は次のとおり書く。地図や外部へのリンクは置かない
  - 日時: 2026年10月31日(土)・11月1日(日) 10:00〜18:00
  - 場所: 東洋大学 赤羽台キャンパス 3201教室
- 本文とスカラベの解説は `[プレースホルダー]` で作り、後から補充する
- 祭の後(11/2 以降)は、アーカイブに切り替える
  - 変える: トップの紹介文の冒頭と、日時と場所の節。過去形(「…に開催しました」)にする
  - 残す: スカラベの解説と展示紹介。展示紹介は文面もそのまま残す
  - 載せない: 当日の報告、来場者数、来場者の写真、参加者のデータ
- 作らないもの: 当日のガイド、展示用端末から誘導するQRコード、参加証ページ、ゲームのプレイ、英語版

### 6.2 名前

- 見出しは「スカラベ・ネットワーク研究会」、その下に「川原研究室|赤羽台祭2026」を添える
- `<title>` は「スカラベ・ネットワーク研究会|川原研 赤羽台祭2026」
- 企画名、祭の名前、日時と場所は1か所(`site.config.ts`)に書く。祭の後の切り替えも、ここを変えて済むようにする

### 6.3 技術選定

研究室サイト(kawahara-lab-site の `docs/spec.md`)と同じ構成にする。

| | 特設サイト `site/` |
|---|---|
| 配信先 | GitHub Pages(`base` は `/akabane2026/`) |
| フレームワーク | Astro 7 + TypeScript。日本語のみで、i18nルーティングは入れない |
| スタイル | 素のCSS + CSS変数。`tokens.css` は研究室サイトの変数名の体系をコピーし、値を祭用に変える |
| ヒーロー | 研究室サイトの `src/hero/`(C-5 有名なグラフ)をコピーする。正本は研究室サイトに置き、テストはコピーしない。図形の切り替えは、研究室サイトでは検証用だが、特設サイトでは公開ページにも出し、いま見えている形の説明を添える |
| チェック | Prettier、astro check、ビルド、ビルド結果の検査(`node --test`)。Vitest と Playwright は入れない |
| ワークフロー | `site/**` が変わったときだけ動かす |

- **1〜5章のビルドなしの方針に合わせない理由**: アプリをビルドなしにしたのは、`static/` を Django にそのまま置けるようにするためである。特設サイトは Django に載らず GitHub Pages で公開し、保守するのは研究室サイトと同じ1人なので、研究室サイトと同じ構成に揃えるほうが楽になる
- **研究室サイトと別にする理由**: 研究室サイトは後輩が何年も保守し、特設サイトは一回きりのため(kawahara-lab-site の `docs/spec.md`「リポジトリと公開先」)
- 内部リンクは研究室サイトと同じく、`base` を付ける関数を通す
- スカラベとグラフを組み合わせたモーションは、内容が固まってから追加で検討する

**ロゴと画像**

- ロゴは `site/src/assets/logo.png` に置き、`<Image>` で表示に合った大きさに縮めて出力する。元のファイルはそのまま配信しない
- ロゴを使うのは、トップの企画名の横と OGP 画像の2か所。ヘッダーとファビコンには使わない(小さく縮めると脚の頂点がつぶれる)
- ロゴの背景は透明ではなく白で塗られている。白地に直接置き、こちらで加工しない。透明な背景の版ができたら差し替える
- スカラベの別のイラストは置かない。ロゴの脚が頂点と辺でできていることを、スカラベの解説で企画のモチーフにした理由として書く
- OGP 画像は、白地の 1200×630 にロゴ、企画名、添え書きを並べ、スクリプトで作る。日時は入れない(アーカイブになっても古くならないように)
- 画像を生成したり、仮の絵を描いたりしない。既存の素材を並べるのはよい

**色**

祭用の色はロゴから取る。ロゴの色は青 `#1b5faa`、シアン `#23c4d6`、金 `#e0a730` の3つ。

- リンクの色 `--color-link` をロゴの青にする(白地で 6.4:1)
- ヒーローの `--accent` をロゴの青、`--accent2` を金にする
- シアンと金は白地で約 2.1:1 しかないので、文字には使わず、装飾(グラフの頂点と辺)だけに使う
- 文字、背景、罫線と `--color-navy` は研究室サイトのままにする
- `tokens.css` を変えたら、ゲームにも同時にコピーする(1章)。サイトとゲームで色をずらさない

### 6.4 研究室サイトとのつながりと告知

- 研究室サイトには告知記事を1本書き、そこから特設サイトへリンクする。研究室サイトの仕様は変えない
- 特設サイトのトップから研究室サイトへリンクする
- 告知記事を出して特設サイトへリンクした時点を、告知の開始とする。それまでは、プレースホルダーのまま公開されていてよい(どこからもリンクしていないため)
- 告知記事を出す条件: 日時と場所、企画の紹介文、一文の紹介(`site.config.ts` の `description`)、展示紹介の文面がそろっていること。一文の紹介は、リンクを共有したときのプレビューに出るので条件に入れる。スカラベの解説、画面写真は条件に入れない
- 告知記事を出す目安は 10/27(ゲームの最終版の翌日)。ただし条件がそろうのが先で、日付を理由に未完成のまま出さない
