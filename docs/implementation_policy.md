- 作成日: 2026-10-06(2026-10-15 改訂: 研究室サイトを別のリポジトリへ移したため、その記述を外した)
- 対象: 基盤に載せるアプリ `apps/*`。展示の特設サイトの方針は、作るときに書く
- 関連: 基盤の要件 `docs/requirements.md`、ゲームの設計 `docs/dijkstra_game_design.md`
- 研究室サイトは [kawahara-lab-site](https://github.com/custard-1855/kawahara-lab-site) で作っている(実装方針は同リポジトリの `docs/spec.md`)

## 1. 技術選定

| | 基盤のアプリ `apps/*` |
|---|---|
| 配信先 | 基盤(Mac / Raspberry Pi、同一LANのみ) |
| 書く言語 | JavaScript(ESモジュール)+ JSDocで型 |
| ビルド | なし。`static/` をそのまま配信する |
| 型チェック | `tsc --noEmit`(`checkJs`)※未導入 |
| テスト | `node --test` |
| 外部依存(実行時) | なし |

- **ビルドなしにする理由**: 基盤は `apps/{name}/static` をそのまま配信する(`docs/requirements.md` 4章)。ビルドを入れると、「`apps/` に置いて再起動するだけで動く」という基盤の利点がなくなる。生成物をコミットすると、元のコードとずれるおそれもある。新しいアプリも、基盤の規約が変わらない限り同じ方針にする
- 型チェックはTypeScriptのコンパイラで行う。JSDocで型を付けておけば、将来TypeScriptに移すときも機械的に書き換えられる

## 2. コードの構成

役割ごとにファイルを分け、**上の層は下の層を使い、下の層は上の層を知らない**。抽象クラスやインターフェースは足さず、「そのファイルが何を知っているか」で分ける。

- 計算(ゲームの規則、探索など)はDOMに依存しないファイルに置き、Node上で直接テストする
- 画面のファイルは状態を持たず、計算の結果を描くだけにする
- 例: 削除前の `apps/dijkstra-delivery/` では、`logic.js` はDOMに依存せず、`view.js` は状態を持たなかった(設計書3.4〜3.5)。研究室サイトのヒーロー(kawahara-lab-site の `src/hero/`)も同じ考え方で分けている
- 検証用の操作は、URLに `?dev` を付けたときだけ出す。公開する画面の見た目には出さない

## 3. コードの書き方

- コメント・テスト名・コミットメッセージは日本語。コメントには「何をするか」より「なぜそうするか」を書く
- 調整用の値(速さ、間隔、数など)は1か所(`config.js` など)に集める
- 乱数を使う処理は `Math.random` を直接使う。テストでは `Math.random` を差し替えて種を固定する

## 4. 作り直しの進め方

1. **先に、今の実装に対するテストを作る**。実装には手を入れない
2. テストが変化を検出できるか確かめる(実装をわざと少し変えて失敗することを見て、元に戻す)
3. 作り直す。挙動を変えない変更(整形、移動、分割、名前の変更)と、挙動を変える変更は別のコミットにする
4. 挙動を変えない変更では、テストを書き換えずに通ることを確認する。テストを直す必要が出たら、実装の仕様を確かめ直し、分かったことを記録する

- テストで見つかった既存の不具合は、すぐ直さずに記録する(`node --test` なら `todo` を付ける)。直す作業は別のコミットにする
