### 参加者の識別と共通アンケートの検討
受付で基本情報を入力し、そのとき発行したもので参加者を識別する仕組みを検討した。検討の順序と結論は次のとおり。

1. 最初の案は、ユニークなQRを発行して読み取る方式だった。しかしLAN内のhttpではブラウザからカメラを使えない。そのため、展示用端末が参加者のQRを読む方式は、そのままでは成り立たない。
2. 利用形態を整理した。展示用端末(PC・タブレット)と参加者のスマホで、別のアプリを配信する予定である。
3. スマホ向けアプリは研究室兼広報用の公開サイトに移すことにした。HTTPSの公開ページからはLAN内のhttpのMacを呼べないので、スマホとMacは別のシステムになる。スマホでの記録は参加者と結び付けない(案A)。
4. 必要なのは「認証」ではなく「識別」と整理した。なりすましより、打ち間違いや前の参加者のログインが残ることによる取り違えのほうが問題になる。
5. 色々なゲームを遊ぶ前提で、共通のアンケートを切り出した。1人1回でよい参加者の属性は基本情報として受付で聞く。楽しさや難しさのように遊んだ直後でないと答えられない設問は、全アプリ共通の体験評価として終了時に聞く。設問の中身は後で決まるので、当面は仮に置く。
6. 紙を使わない方式にした。来場者は大学のWi-Fiに接続できないので、参加者のスマホはLANに参加しない。受付で発行したコードは、公開サイト上の静的な参加証ページで持ち歩いてもらう。

検討した主な選択肢と、採用しなかった理由は次のとおり。

| 案 | 採用しなかった理由 |
|---|---|
| 展示用端末に表示したQRを、ログイン済みのスマホで読んで紐付ける | スマホがLANに参加しないので、Macと通信できない |
| 番号カードや印刷したQR | 紙を使いたくない |
| NFCカード | タブレットにつなげるリーダが限られる。費用もかかる |
| 一覧から名前を選ぶ | 予備の手段として未確定事項に残した。一般向けサーバから参加者の情報を読み出すことになり、6章ルール5の例外となる |
| スマホの記録も参加者と結び付ける(案B) | 公開サイトにバックエンドが必要になる。研究データを学外に置く規程の確認も要る。再検討のトリガーとして9章に残した |
